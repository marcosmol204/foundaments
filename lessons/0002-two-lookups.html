MongoDB Internals · Lesson 0002 · Phase 1: The engine

Two lookups

You already use indexes. Here is what an index and a collection actually are inside the storage engine.

Your win today: look at an explain() plan and describe, in engine terms, exactly which data structures MongoDB touched and how many times.

1 · Two layers inside one mongod

A single mongod process holds two very different pieces of software:

  • The MongoDB layer understands documents, query filters, aggregation, replication and sharding. Everything you've used so far lives here.
  • The storage engine, WiredTiger, understands much less: tables of sorted keys and values, plus transactions, caching and durability.WT B-trees

They talk through a small, fixed interface, the storage engine API. Its two main pieces map onto things you know:storage README

You know it asMongoDB layer calls itWiredTiger stores it as
a collectionRecordStorea table: RecordId → BSON document
an indexSortedDataInterfacea table: index key → RecordId

A RecordId is the storage engine's internal address for a document. Indexes point to RecordIds, so changing a document's RecordId would be expensive: every index entry for that document would have to change.storage README Each table is its own file on disk, called an ident: collection-<id>.wt or index-<id>.wt. You'll see them in the lab.

2 · Every table is a B-tree

WiredTiger keeps each table as a B-tree, a tree of pages. "The root and internal pages only store keys and references to other pages, while leaf pages store keys and values." Records are kept sorted by key.WT arch guide

Two operations follow from that shape:

  • Seek: walk from the root down to the one leaf where a key belongs. This takes only a few page hops, even for huge tables.
  • Range scan: once at a leaf, read keys in sorted order until they stop matching.

Take your reviews collection with a compound index {verified: 1, rating: 1}. Its keys are sorted by verified first (false before true), then by rating. So all the {verified: true, rating: 5} entries sit next to each other. That is the real reason prefix rules exist: the engine can seek to verified: true because verified comes first. It can't seek straight to rating: 5, because those entries are split between the false part and the true part of the tree. In the lab, the planner chose a full collection scan for find({rating: 5}).

2b · B-tree concepts, step by step added after your feedback

Before the two-tree picture, here is one tree, slowly: the reviews collection table. Its keys are RecordIds. To keep it simple, there are only nine reviews, with RecordIds 1 … 9.

The vocabulary

TermWhat it is
PageA block of sorted entries. It is the unit WiredTiger reads from disk, keeps in memory, and writes back. A tree is made of pages.
Leaf pageThe bottom level. It holds the real data: key/value pairs in sorted order. In a collection table, a leaf holds RecordId → document. In an index table, it holds index key → RecordId.
Internal pageA signpost. It holds only separator keys and pointers to child pages, never the data itself. "Keys below 4, go left."
Root pageThe top internal page. Every search starts here.
DepthThe number of levels from root to leaf. A seek visits one page per level.
SplitWhen a page reaches its size limit, it splits in two. That's how the tree grows.WT B-trees

Walkthrough 1 · Seek for RecordId 8

  1. Start at the root. It has separators 4 and 7, which split the key space into three ranges.
  2. Compare: 8 ≥ 7, so follow the third pointer.
  3. You land on the third leaf. Search inside that page and find 8 along with its value, the review document.

That's 2 page visits (2 levels). Internal pages hold many separators each, so trees stay shallow even when they're large. Our 200,000-document lab collection had a depth of just 3.

Walkthrough 2 · Range scan from 4 to 8

  1. Seek to 4 (root → middle leaf).
  2. Read 4, 5, 6 in order. The page ends, so the cursor moves on to the next leaf in key order.
  3. Read 7, 8. The next key, 9, is past the end, so stop.

This is exactly what IXSCAN does in an index tree: one seek, then read in sorted order. Every key it reads counts toward keysExamined. A COLLSCAN is the same walk over every leaf of the collection tree.

Pages live in two places

Every page has an on-disk form, compressed inside the .wt file, and an in-memory form that WiredTiger reads into its cache.WT B-trees When you update a document, WiredTiger doesn't rewrite the page on the spot. It chains the change onto the in-memory page, in a list called the update list.WT B-trees Changed pages are written back to disk later. Lesson 3 (the cache) is about that "later".

Where does the journal fit? It doesn't. It isn't part of any B-tree.

The B-tree .wt files are the organised copy of your data. WiredTiger writes a consistent copy of them to disk at each checkpoint, every 60 seconds.docs The journal is a separate, append-only log (journal/WiredTigerLog.*, ~100 MB files). It records every change made since the last checkpoint and is synced to disk every 100 ms.journaling

An analogy: the B-tree is a printed book, reprinted every 60 seconds. The journal is a diary of edits since the last printing. After a crash: take the last printing, then replay the diary. That's lesson 5.

Counting files (you missed Q6, so here it is once more)

One table per collection + one table per index. store.reviews has the _id index (always created) and verified_1_rating_1. That's 1 + 2 = 3 files: collection-7, index-8, index-9. With three indexes in total, it would be four.

2c · Now, two trees together

The picture below is just two of the trees above, side by side. On the left is the index table for {verified: 1, rating: 1}. Its keys are pairs, (true, 5), meaning verified true, rating 5, sorted by verified and then by rating. Equal keys are allowed, since many reviews are verified 5★. Each key points to a RecordId (→ 58). On the right is the collection table. Its keys are RecordIds, and each points to the full review. The arrows show how a RecordId found in the index leads to a document in the collection.

Reading it for find({verified: true, rating: 5}):

  1. Seek in the index tree: root → the highlighted leaf where (true, 5) keys start. (Walkthrough 1, in the left tree.)
  2. Scan: read the three (true, 5) entries in order, then stop at the first key that isn't (true, 5). That's 3 keys examined, giving RecordIds 8, 58 and 108. (Walkthrough 2.)
  3. FETCH: for each RecordId, do a fresh seek in the collection tree (root → leaf) to get the review. That's 3 docs examined.
  4. Total work: 1 index seek + 3 keys + 3 collection seeks. Notice the verified 5★ reviews are not next to each other in the collection tree (8, 58, 108). That's why each needs its own seek.

A covered query is one where the index key alone holds every field you asked for. Then there is no FETCH at all: one B-tree instead of two.explain docs Note that _id is returned by default. If it isn't in the index, the query isn't covered.

3b · From Q3 to a best practice: cover your hot queries added after your feedback

Q3 asked which query avoids FETCH. That turns into a real performance rule:

For a query that runs very often, make it covered. Put every field it filters on, sorts on and returns into one index, and project only those fields, with _id: 0 unless _id is in the index.

Measured on the lab server (200k reviews, ~164-byte documents)

Query find({verified: true, rating: {$gte: 4}}), the verified positive reviews, matches 97,789 reviews, with index {verified: 1, rating: 1}. Best of 5 runs:

VariantPlankeysdocstimebytes returned
No projectionFETCH ← IXSCAN97,78997,78944 ms15.6 MB
{rating: 1}PROJECTION_SIMPLE ← FETCH ← IXSCAN97,78997,78957 ms3.2 MB
{_id: 0, rating: 1}PROJECTION_COVERED ← IXSCAN97,789031 ms1.6 MB

Three lessons hide in that table:

  1. The win comes from removing FETCH, not from projecting. Row 2 projects too, but still returns _id, so it still does 97,789 collection seeks. Inside the database it was even a bit slower, since it adds a projection stage. Projection alone only saves network bytes.docs
  2. It gets better when data is cold. My data was all in cache, so the gap was only 44 → 31 ms. Index keys are smaller than documents and are "typically available in RAM". Documents may have to come from disk, and then each FETCH can cost a disk read.docs
  3. Less data over the wire. 15.6 MB → 1.6 MB for the same rows, mostly because the review text stays behind. Your app server feels that too.

When a query can't be covered

The official rules:docs

  • Every field in the filter and every returned field must be in the same index.
  • No equality-to-null predicates ({field: null}).
  • Multikey indexes can't cover queries over the array fields.
  • On a sharded cluster (via mongos), the index must contain the shard key.
  • Not every index type supports covering.

The trade-off: don't widen every index

"In write operations, MongoDB must both write the change to the collection and update the index."docs In engine terms: every index is one more B-tree that every insert has to modify, and every update too if it changes an indexed field. Extra fields also make the index's pages bigger, so they take more cache. Cover the few queries that dominate your traffic, not all of them.

Check it worked: in explain("executionStats"), you want totalDocsExamined: 0 and no FETCH above the IXSCAN. On 8.0, the top stage shows as PROJECTION_COVERED.
