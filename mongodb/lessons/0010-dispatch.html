Command dispatch and interruption

Hop 4: what the server does between "a message arrived" and "the command's code runs", and how a running command is stopped by maxTimeMS or killOp.

Your win today: a runaway db.reviews.find({review: /battery/i}) is scanning your 5-million-review collection. You find it in $currentOp, kill it safely, predict how fast it stops and what stays changed, and prove all of it from the slow-query log line. This is the "diagnose a production symptom" goal from your mission, for hop 4.

  1. In lesson 6, the insert with w: "majority" waited for the secondaries. On which thread did it wait, and in which hop's code?

Answers: (1) the connection's own thread, inside dispatch, after the command ran (RunCommandAndWaitForWriteConcern). (2) One. (3) COLLSCAN, which reads all 5 million documents. Keep (1) in mind: section 1 shows where that wait sits.

1 · From message to run(), step by step

We follow one command: db.reviews.find({review: /battery/i}).maxTimeMS(1000). Everything here is the server source at tag r8.0.34, the version in the lab. The main file is service_entry_point_common.cpp; the doc for the whole hop is docs/command_dispatch.md.

  1. The OperationContext already exists. Hop 3 creates it when it turns the message into a WorkItem (initOperation).session_workflow.cpp Every operation has one. It holds the operation's opid, its deadline, its kill flag, its locks and its storage transaction. Remember the deadline and the kill flag: section 2 is about them.
  2. Pick a path by opCode. handleRequest → runOperation switches on the header's opCode. OP_MSG (2013, lesson 8) goes to receivedCommands. OP_INSERT, OP_GET_MORE and the other legacy opcodes fail with "no longer supported".runOperation
  3. Parse the message. parseCommand turns the bytes into an OpMsgRequest: the body document plus any kind-1 document sequences.parseCommand The command's name is simply the first field of the body: find.op_msg.h
  4. Find the command. Every command registers itself in a global CommandRegistry at startup.command_dispatch.md findCommand("find") looks it up. An unknown name fails with CommandNotFound (59), "no such command".executeCommand
  5. Parse the generic arguments, then the command. Some fields mean the same thing for every command: $db, maxTimeMS, readConcern, lsid, comment. _parseCommand reads them first. Then CurOp records the command body, so from here on $currentOp can show it. Last, command->parse() builds a CommandInvocation: one parsed, ready-to-run instance of find._parseCommandcommands.h
    About $db: the server keeps no "current database" for a connection. Every command carries $db, and use store in mongosh only changes what mongosh puts there. $db: "store" plus find: "reviews" gives the namespace store.reviews. In the lab, an Unauthorized error message echoed the whole body back, ending in $readPreference: { mode: "primaryPreferred" }, $db: "store".
  6. The checks before running (_initiateCommand). In this order:_initiateCommand
    • Start the clock (startedCommandExecAt). The maxTimeMS budget is counted from here, so reading the socket and parsing are not in it.L1636
    • Authorization: checkAuthorization throws Unauthorized (13). In the lab, a user without read access on store got Unauthorized in 5 ms, before any scanning.L1731
    • Can it run on this node? A write on a secondary fails with NotWritablePrimary (10107); a read without a secondary-ok read preference with NotPrimaryNoSecondaryOk (13435).
    • The deadline: setDeadlineByDate(startedCommandExecAt + maxTimeMS, MaxTimeMSExpired). If the client sent no maxTimeMS and the command is a read, 8.0 can use the defaultMaxTimeMS cluster parameter instead (section 4).L1808
    • Read concern: the client's, or the cluster default if the client set no level. On a replica set, the slow log says where it came from: readConcern: {level: "local", provenance: "implicitDefault"} in every lab line._extractReadConcern
    • One interrupt check, then CurOp::ensureStarted(): by now CurOp's timer is running.L1927
  7. Run it (_commandExec). First wait for the read concern if needed (for example afterClusterTime).L1955 Then, if the command takes a write concern, RunCommandAndWaitForWriteConcern: run, then wait for w, all on this thread. That's warm-up answer 1, and lesson 6's hop 8. Otherwise RunCommandImpl. Both end in invocation->run(opCtx, reply), the command's own code.CommandInvocation::run For our find: plan a COLLSCAN, fill the first batch (101 documents), and park the rest of the scan in a cursor for later getMores.
  8. Log it (completeOperation). CurOp::completeAndLogOperation stops the clock, computes durationMillis and workingMillis, and writes the "Slow query" line if the time is at least slowms (100 ms by default). It writes it for failed commands too, with errCode and errName.completeOperationcurop.cppslowMS Then the reply goes back to hop 3, which writes it to the socket.

So CurOp knows the command from step 5, its timer runs by the end of step 6, and it stops in step 8. $currentOp shows the operation in between, and durationMillis measures roughly steps 6 to 8. That is why a maxTimeMS: 1000 error can log durationMillis: 998: the deadline clock started a little earlier (step 6, first line) than CurOp's timer.

2 · How a running command is stopped

Now the find is in step 7, scanning. Two things can stop it: its own deadline, or somebody's killOp. Both work the same way, and neither one stops the thread from the outside.

  1. A kill only sets a flag. killOp finds the target's OperationContext and calls markKilled(Interrupted), which stores the error code in an atomic field.service_context.cppoperation_context.h Then it returns {info: "attempting to kill op", ok: 1}. The source says it plainly: "killOp always reports success once past the auth check."kill_op.cpp
  2. The running thread must look at the flag. It does that in checkForInterrupt, which checks, in order: client killed, shutdown, deadline passed → MaxTimeMSExpired (50), kill flag set → Interrupted (11601), and, for find and count, whether the client has disconnected.checkForInterruptNoAssertfind_cmd.cpperror codes So maxTimeMS is not a timer that fires. It is a time check inside the same function. The manual: MongoDB "terminates operations that exceed their allotted time limit using the same mechanism as db.killOp()" and "only terminates an operation at one of its designated interrupt points."cursor.maxTimeMS
  3. A scan checks at its yield points. The query executor asks "time to yield?" as it goes. The answer is yes every internalQueryExecYieldPeriodMS = 10 ms by default.query_knobs.idlplan_executor_impl.cpp At a yield it checks for interrupts, releases its locks and storage snapshot, and takes them again. Waits on a condition (a lock, a ticket, the write concern) wake up for a kill or a deadline too.waitForConditionOrInterrupt In the lab, a 1-second scan logged about 60 numYields and 129 numInterruptChecks.
  4. So between two checks, nothing can stop it. If one stretch of work takes 3 seconds, a kill waits 3 seconds. In the lab I made that happen on purpose: I set internalQueryExecYieldPeriodMS to 5,000 (a test knob; never do this in production), so a 2.2-second scan never reached a check. Inside a multi-document transaction, queries never yield (they can't release their snapshot), but they still check for interrupts on the same timer.plan_yield_policy.cpp

A cursor's budget is server time

Our find returns its first 101 matches in about 1 ms. The rest of the scan happens in getMores. Each getMore gets the time the cursor has left as its deadline.getmore_cmd.cpp In the lab, find(…).maxTimeMS(1000) iterated in mongosh failed in its fifth or sixth getMore: 1,010–1,023 ms of server time in total. But mongosh waited 7.3–7.8 s, and received 480,000–490,000 reviews first. The manual says it: "MongoDB does not count network latency between the client and the server towards a cursor's time limit."cursor.maxTimeMS The time your app spends between batches isn't counted either.

The fix is timeoutMS, the driver's client-side operation timeout (CSOT). It counts wall-clock time for the whole operation: server selection, pool checkout, the find and every getMore.CSOT spec The driver still sends maxTimeMS (remaining time minus the server's minimum round trip), so the server stops too. With Node driver 7.7.0 and timeoutMS: 1000, the same loop failed with MongoOperationTimeoutError after 1,003–1,070 ms of wall clock. The driver sent maxTimeMS: 1000 on the find (the round trip rounds to 0 ms on one machine), and then a killCursors, so the server didn't keep a half-read cursor.

3 · Find and kill a runaway operation

In production you rarely know the opid. You find it with $currentOp on the admin database:$currentOp

db.getSiblingDB("admin").aggregate([
  { $currentOp: { allUsers: true } },
  { $match: { active: true, secs_running: { $gte: 5 }, client: { $exists: true }, ns: /^store\./ } },
  { $project: { opid: 1, secs_running: 1, op: 1, ns: 1, planSummary: 1, appName: 1,
                client: 1, numYields: 1, killPending: 1, comment: "$command.comment" } }
])

What it returned in the lab, for a scan started with {comment: "lab10-runaway"}:

{ client: '127.0.0.1:59678', appName: 'mongosh 2.13.0', opid: 397313,
  secs_running: Long('1'), op: 'command', ns: 'store.reviews',
  planSummary: 'COLLSCAN', numYields: 75, comment: 'lab10-runaway' }
  • secs_running is whole seconds since CurOp started (microsecs_running is precise). Your filter.
  • planSummary: 'COLLSCAN' on a big collection is the usual suspect.
  • appName and client say which service sent it. Set appName in every connection string, so this field names your service and not just "Node driver".
  • client: {$exists: true} keeps only operations from client connections. Internal operations (replication, TTL, index builds) are not yours to kill. The manual: "Only use killOp to terminate operations initiated by clients", and never use it on index builds; use dropIndexes.killOp
  • numYields going up between two looks means it is reaching interrupt points, so a kill will land quickly.

Then db.killOp(opid). Don't trust its ok: 1: run $currentOp again. Either the op is gone, or it shows killPending: true, which means it hasn't reached its next interrupt point yet.killOp

What a kill rolls back, and what it doesn't

The kill makes the command throw at its next check. Whatever was already committed stays committed. Lesson 6's rule decides what that means:

  • A read: nothing to undo. The cursor is freed.
  • A single-document write: one WriteUnitOfWork, so all or nothing (lesson 6).
  • A multi-document write without a transaction is not one unit. "The modification of each document is atomic, but the operation as a whole is not atomic."atomicity In the lab, I added a field flagged: true (a moderation flag, only for this test) with updateMany({review: /battery/i}, …) and killed it after 1.6 s. 172,232 reviews stayed flagged. The client got only Interrupted, with no count of what changed, and the slow-log line had no nModified either. Those changes are in the oplog, so the secondaries have them too.
  • Inside a transaction: killing one statement aborts the whole transaction. In the lab, a transaction updated one review, then its countDocuments was killed. The commit failed with NoSuchTransaction (251), and the earlier update was gone.

So before you kill a write, decide whether "half done" is OK. If it isn't, make the job resumable (a filter that skips finished documents, such as {flagged: {$ne: true}}), or run it in batches.

6 · So in production you should…

Rule: give every user-facing query a deadline the server enforces (timeoutMS in the driver, which sends maxTimeMS), and treat killOp as a request, not a guarantee: confirm it, and know what a half-finished write leaves behind.

  1. Set timeoutMS on the client (CSOT, or per operation). It bounds what the user actually waits: 1.0 s in the lab, against 7.3–7.8 s for maxTimeMS(1000) alone. It also bounds the pool wait from lesson 7. If your driver has no CSOT yet, set maxTimeMS on every query, and remember it only counts server time.
  2. Add a server-side safety net. In 8.0, setClusterParameter: {defaultMaxTimeMS: {readOperations: …}} gives every read without its own maxTimeMS a deadline.default_max_time_ms In the lab with readOperations: 200, an app user's full scan failed with MaxTimeMSExpired after 203–210 ms. A query with its own maxTimeMS: 5000 still finished (369 ms). It applies only to reads, and users with the bypassDefaultMaxTimeMS privilege skip it: root did, and so does everyone when auth is off.
  3. Tag queries with appName (per service) and comment (per code path). Then $currentOp and the slow log tell you who to call.
  4. Kill safely: filter $currentOp by active, secs_running, client and ns; kill by opid; check again for killPending. Never kill internal operations or index builds.
  5. Make long writes resumable, because a killed updateMany keeps everything it already did (172,232 reviews in the lab) and doesn't tell you how many.
  6. Fix the cause, not just the symptom. A deadline stops a COLLSCAN; an index prevents it. For word search in reviews, a text or Atlas Search index fits better than /battery/i.
