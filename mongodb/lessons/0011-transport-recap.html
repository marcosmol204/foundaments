MongoDB Internals · Lesson 0011 · Phase 2: Transport & wire (recap)

Diagnose a latency spike across hops 1–4

Lessons 7 to 10 each opened one hop. This lesson puts them back in a line, as one time budget, and gives you a method: four measurements, three subtractions, and the biggest gap names the hop.

Your win today: someone tells you "p99 of find({rating: {$gte: 4}}) on store.reviews jumped from 20 ms to 900 ms". You split that time into hops 1–4, say which hop grew, and name the one metric that proves it. Then you do it for real, on a lab cluster with a hidden fault. This is goal 1 of your mission ("diagnose a production symptom by naming the internal mechanism behind it and the metric that proves it"), for the whole transport layer.

0 · Warm-up from lessons 7 to 10

From memory, before reading on.

  1. Lesson 7: 40 slow finds, maxPoolSize: 5. The slow log said ≈ 103 ms, the app saw ≈ 550 ms. Where were the other 450 ms?
  2. Lesson 7 again: with maxPoolSize: 40, durationMillis was ~585 ms but workingMillis only ~170 ms. What was the find doing for the difference?
  3. Lesson 9: what is mongod's thread for an idle pooled connection doing right now?

Answers: (1) in the driver's wait queue, waiting to check out a connection; (2) waiting in mongod for an execution ticket; (3) sleeping in sourceMessage. If all three came back, you already have the method. Section 1 just puts it on one line.

1 · One request as a time budget

Take one find, from the moment your code calls it to the moment it gets the documents. Every millisecond of it sits in one of these segments, in this order:

You can't time each segment directly. But four numbers are easy to get, and each one covers a known part of the bar:

  1. App sees. Your own timer around the call. Everything.
  2. Command duration (driver). The driver's command monitoring event (commandSucceeded / commandFailed) times one command from "sent" to "reply received". The spec allows it to include BSON encoding and decoding.command monitoring spec It does not include server selection or the pool checkout, which happen before the command exists on a connection. The checkout itself has its own event: connectionCheckedOut.durationMS.CMAP spec
  3. durationMillis (slow-query log, or the profiler). CurOp's clock, which starts in dispatch, after the bytes were read and parsed, and stops when the reply is built (lesson 10, steps 6 to 8). So it doesn't contain the network.
  4. workingMillis. durationMillis minus the time the operation was blocked: lock waits, the queue for execution tickets, and flow control.curop.cpp L568L642 The ticket wait is also logged on its own, as queues.execution.totalTimeQueuedMicros.

Then subtract:

GapWhat lives in itHopLesson
app sees − command durationserver selection; pool checkout (with a new connection's setup, if one was opened)17
command duration − durationMillisnetwork round trip and transfer, compression, the server's thread reading the socket and parsing238, 9
durationMillis − workingMilliswaiting for an execution ticket, a lock, flow control47, 10
workingMillisthe work itself: plan, scan, cache misses, and for writes the write-concern wait (waitForWriteConcernDurationMillis)4 and below6; Phase 3

Two cautions from earlier lessons. A cursor is many commands: the slow log has one line per find and per getMore, and the time your app spends between batches is in no server number at all (lesson 10: 1,017 ms of server time, 7.4 s of waiting). And the server can't see hop 1 at all: if you only read the slow log, a pool problem looks like "the server is fast, so it's not the database".

2 · The walkthrough: one spike, four subtractions

One real example from this lesson's lab, step by step. The lab is a 3-member replica set on mongo:8.0 (8.0.34) in Docker, -m 1g each, 1,000,000 seeded reviews, and an index {rating: 1} so our query is a plain IXSCAN. The app, reviews-api, is 8 workers looping find({rating: {$gte: 4}}).limit(20) on the Node.js driver 7.7.0 (the same version as lessons 7 and 10), maxPoolSize: 10. Healthy, it does about 600 finds a second at p50 1.3–1.5 ms, p99 3.4–3.9 ms. The lab can't give you 20 → 900 ms exactly, but it gives the same shape: a p99 that grows 20× to 60×.

  1. The symptom. p99 went from ~3.6 ms to 72–227 ms (three runs), with no errors. The app's view, from load: 
                             p50      p99      max   (ms)
app sees                   41      227      377
checkout wait             0.0      0.0       36
command (wire+server)      41      226      376
mean per op: app 55 = checkout 0.1 + command 55 + other 0.4 (selection, driver)
  2. Hop 1? No. App time ≈ command time. Checkout p99 is 0.0 ms and "other" (server selection) is 0.4 ms. The driver got a server and a connection at once.
  3. Hops 2–3? No. The slowest sampled slow-log line for our find said durationMillis: 245, about the command time. The driver's RTT to the primary stayed at a few milliseconds (4–9 ms; 2–6 ms when healthy). The time is inside mongod's clock.
  4. Hop 4: waiting or working? The same line: 
    "command":{"find":"reviews","filter":{"rating":{"$gte":4}},"limit":20, …}, "appName":"reviews-api",
"planSummary":"IXSCAN { rating: 1 }", "keysExamined":20, "docsExamined":20, "nreturned":20,
"cpuNanos":202915, "numYields":0,
"queues":{"execution":{"admissions":2,"totalTimeQueuedMicros":245360},"ingress":{"admissions":1}},
"workingMillis":0, "durationMillis":245
    workingMillis: 0, 20 keys, 0.2 ms of CPU: the query itself is as cheap as ever. All 245 ms are totalTimeQueuedMicros: it waited for an execution ticket. Over a minute of samples, our finds had durationMillis p99 96 ms and workingMillis p99 1 ms.
  5. Who holds the tickets? Execution tickets limit how many operations run in the storage engine at once; in 8.0, throughput probing raises or lowers that number based on measured throughput.execution control README serverStatus().queues.execution.read showed out 61–63 of totalTickets 66–70. And $currentOp, grouped by appName: 
    admin-search: 64 running, plan COLLSCAN, max secs_running 5, maxTimeMS set: none
    An internal search page runs countDocuments({review: /battery/i}) in 64 parallel loops, with no time limit. Each one scans all 1,000,000 reviews (3.3–5.4 s, 100–165 yields). It holds a ticket while it works and queues for a new one after each yield (one search's own line: admissions: 102, 1,278 ms queued). Our tiny find waits in the same line.
  6. Name it, prove it, fix it. Mechanism: runaway scans with no deadline fill the read tickets, so other reads queue in hop 4. Proof: durationMillis − workingMillis (equivalently totalTimeQueuedMicros) is the whole spike, and $currentOp shows who holds the tickets. Fix now: killOp them by opid and check for killPending (lesson 10). Fix for good: timeoutMS on the search client, a defaultMaxTimeMS.readOperations safety net, and a real index for word search instead of /battery/i. In the lab, stopping the searches brought p99 back to 3.6–3.9 ms.

Notice what the slow log of our find did not show: COLLSCAN, many docsExamined, high cpuNanos. If you had only looked for "slow query plans", you'd have found nothing wrong with it. The gap told you to look at the neighbours.

4 · Case files

Four more faults from the same lab. For each: read the evidence, say the hop and the proving metric out loud before you open the answer. That's the retrieval that makes it stick.

Case A · "The export feature shipped this morning"

p99 of our find went from 3.6 ms to over a second. No errors. The only change today: a CSV export of positive reviews that mention a refund, in the same service.

                         p50      p99      max   (ms)
app sees                  310    1,209    1,218
checkout wait             309    1,207    1,214
command (wire+server)     1.0       21       25

slow log (5% sample), finds on store.reviews by appName and filter shape:
  reviews-api {rating}         IXSCAN { rating: 1 }: durationMillis p50 0     p99 0
  reviews-api {rating, review} IXSCAN { rating: 1 }: durationMillis p50 1098  p99 1558
$currentOp:  reviews-api: 10 running, plan IXSCAN { rating: 1 }

Which hop? Which number proves it?

Answer

Hop 1, the pool. App ≈ checkout wait; command time p50 is still 1.0 ms and our find's durationMillis is 0. The proof is connectionCheckedOut.durationMS (p99 1,207 ms), and $currentOp showing exactly maxPoolSize = 10 operations from reviews-api. They're the export: 12 export workers share our MongoClient, each export find runs 1.1–1.6 s, so they hold all 10 connections and our fast finds wait in the same queue (lesson 7). Note the trap: $currentOp shows reviews-api and the same IXSCAN { rating: 1 } plan. Only the filter shape ({rating, review}) tells the export apart, so tag code paths with comment.

Fix: give the export its own MongoClient with a small pool (one pool per client, per server), or limit its concurrency; set timeoutMS so a pile-up fails fast; and give the export an index that fits it. In the lab, maxPoolSize: 100 also helped (p99 13 ms): the 12 exports no longer block the pool, but now they run on the server and our finds queue a little for tickets there (durationMillis p99 8 ms, workingMillis p99 1 ms). That's lesson 7's "a bigger pool moves the queue". It's only small here because there are 12 slow scans, not 64 as in the walkthrough.

Case B · "The new deploy won't start"

A colleague just deployed a new service, recs-service: 40 instances with minPoolSize: 10. Now every new reviews-api instance fails at startup. Old instances still serve. (The lab sets maxIncomingConnections: 400, with 127.0.0.1 exempt, so this fits on a laptop.)

startup attempt 1 failed after 5,009 ms: MongoServerSelectionError: connection <monitor> to 172.18.0.2:27017 closed
startup attempt 2 failed after 5,009 ms: MongoServerSelectionError: connection <monitor> to 172.18.0.2:27017 closed

lab11-m1 current 405 available -5 active 43 rejected 3051 · refused/60s 2931
lab11-m2 current 405 available -5 active 41 rejected 3165 · refused/60s 3045
connections by appName on m1:  recs-service: 390 connections, 40 active · mongosh 2.13.0: 5 · OplogFetcher: 2

{"ctx":"listener","msg":"Connection refused because there are too many open connections",
 "attr":{"remote":"172.18.0.5:36400","connectionId":22553,"connectionCount":400}}

Which hop? Which number proves it?

Answer

Hop 3, the connection limit. The error looks like hop 1 (server selection), but selection failed because the driver's monitor sockets were refused at accept time: the server is at its limit. Proof: connections.available ≤ 0 and rejected rising on every member, plus the "Connection refused" log line from the listener thread (lesson 9). Who: recs-service holds 390 of 400 on the primary. minPoolSize applies to every member, so 40 × (10 + 2 monitoring) = 480 per member, more than the limit. Its pools keep retrying, which is why rejected climbs by thousands a minute. "40 active" are its 40 parked streaming hellos, not work.

The 5 extra connections over the limit are the exempt mongosh: without maxIncomingConnectionsOverride you couldn't even look. In production the limit is min(maxConns, the file-descriptor rule, 20% of memory ÷ 16 KiB): 13,107 in a 1 GB container.

Fix: do the fleet math before deploying (instances × (pool + 2) per member), drop or shrink minPoolSize, keep admin IPs exempt, and consider the establishment rate limiter with a queue for storms (lesson 9).

Case C · "Eight errors and a five-second hole"

For a few seconds, every request hung, then 8 failed. Then everything was normal again. The app sets serverSelectionTimeoutMS: 5000.

ops ok 12,535, errors 8
  8 × MongoServerSelectionError: getaddrinfo ENOTFOUND m1
                         p50      p99      max   (ms)
app sees                  1.4      3.6    5,014
checkout wait             0.0      0.0       10
command (wire+server)     1.0      3.0       11
mean per op: app 7.5 = checkout 0.0 + command 1.3 + other 6.2 (selection, driver)
p99 per 5 s: 0s 3.8 | 5s 3.6 | 10s 5,014 | 15s 3.7 | 20s 3.3
driver events: connections created 16, pool cleared 1
  +7.9 s m1:27017 RSPrimary -> Unknown
  +7.9 s pool cleared m1:27017
  +17.3 s m2:27017 RSSecondary -> RSPrimary

Which hop? Which number proves it?

Answer

Hop 1, server selection: no primary. Checkout and command times never moved; the whole hole is in "other", the time before a connection is even requested. Proof: the SDAM events, m1 RSPrimary → Unknown plus pool cleared (a network error, so a crash, not a step-down), and a new primary 9.4 s later (8.3–9.4 s in two runs; lesson 7 measured 10.8 s). That's the election timeout: nobody nominated a successor. The 8 errors are the 8 workers whose selection ran out its 5 s budget before the election finished. (ENOTFOUND is a Docker detail: a killed container's hostname disappears. In production you'd see a timeout or "connection refused".)

With the default serverSelectionTimeoutMS of 30 s, the same crash gives no errors and a ~10 s request, as in lesson 7. Neither is wrong; choose on purpose.

Fix: prefer planned step-downs for maintenance (30 ms in lesson 7). Make your request budget (timeoutMS) and retry policy fit a ~10 s election, and keep retryable reads/writes on.

Case D · "Everything is 40 ms slower"

Not a spike, a shift: every request got slower by the same amount, p50 and p99 alike. The infra team "moved some network things" last night.

                         p50      p99      max   (ms)
app sees                   45       54      248
checkout wait             0.0      1.0      206
command (wire+server)      44       53       55
topology at end: m1 RSPrimary rtt 42 ms · m2 RSSecondary rtt 3.0 ms · m3 RSSecondary rtt 5.0 ms

slow log, reviews-api {rating} IXSCAN { rating: 1 }: durationMillis p50 0 · workingMillis p50 0

Which hop? Which number proves it? And why is checkout max 206 ms?

Answer

Hop 2, the network to the primary. Command ≈ app, so not hop 1. durationMillis is 0, so command − durationMillis ≈ 44 ms is all outside mongod's clock. Proof: the driver's own RTT to m1 is 42 ms, while m2 and m3 are 3–5 ms. (The lab added 40 ms with tc netem on m1's network interface, the same tool as lesson 8.) A limit(20) reply is a few KB, so this is latency, not bandwidth: compression wouldn't help.

The 206 ms checkout is a new connection being opened at startup: TCP, the hello handshake and the first command are several round trips, each 40 ms (lesson 7). Slow links make cold pools expensive.

Fix: put the app in the same zone as the primary, and cut round trips per user request (batch writes, one query instead of three). Each round trip you remove saves 40 ms here.

5 · So in production you should…

Rule: record four numbers for every slow request (app time, checkout wait, command duration, and the server's durationMillis / workingMillis), subtract, and go to the hop with the biggest gap. Don't start with the query plan.

  1. Make hop 1 visible. Export CMAP checkout time and command duration to your APM, per service. The server will never show you hop 1.
  2. Tag everything. appName per service and comment per code path. In case A, only the filter shape told the export apart from our find; a comment would have named it.
  3. One client per workload. A pool belongs to one MongoClient. Don't let batch jobs and user requests share it.
  4. Give every request a budget with timeoutMS: it bounds selection, checkout and server time together (lesson 10). Add defaultMaxTimeMS.readOperations as the server-side net for clients you don't control.
  5. Do the connection math fleet-wide before each deploy, and keep an exempt way in for admins (lesson 9).
  6. Watch the ticket queue. Alert on durationMillis − workingMillis (or queues.execution.totalTimeQueuedMicros) for your critical queries. When it grows, look at $currentOp, not at your query.
