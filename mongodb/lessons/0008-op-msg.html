MongoDB Internals · Lesson 0008 · Phase 2: Transport & wire

OP_MSG in depth

Lesson 6 showed one insert as one 483-byte OP_MSG with nothing special in it. This lesson opens the parts that were empty there: the three flag bits, the second kind of section, and the compressed wrapper. Hop 2, all the way down.

Your win today: read one line of a wire capture and say, from the bytes alone, whether a reply will come, how many replies will come, how the reviews are packed, and whether (and how) the message is compressed. Then use measured numbers to choose batching, compression and write concern for a real link. This is hop 2 of the "trace one write end to end" goal in your mission.

1 · The message, one more time

Every message starts with the same 16-byte MsgHeader: messageLength, requestID, responseTo, opCode, all little-endian. A reply's responseTo is the request's requestID.wire protocol (9.0) After that, an OP_MSG (opCode 2013) has three parts:OP_MSG spec

  1. flagBits, 4 bytes: what the receiver should expect (section 2).
  2. One or more sections, each starting with one kind byte. Exactly one kind 0 (the command body). Kind 1 is a document sequence (section 3).
  3. An optional CRC-32C, 4 bytes at the end, only if checksumPresent is set.

And any message can be wrapped in OP_COMPRESSED (opCode 2012, section 4). Here are three real messages from this lesson's lab, drawn to the same pattern (not to scale):

Lab setup for all numbers below: mongo:8.0 (8.0.34) standalone in Docker, 250,000 seeded reviews (avg 164 B), and two clients on the same Docker network: pymongo 4.19 (in a python:3.12-slim container) and mongosh 2.13 (Node driver 7.5.0). Each capture was taken with tcpdump next to mongod and decoded with this lesson's parser, lessons/code/0008-opmsg.py.

2 · flagBits: three bits that change the conversation

OP_MSG is request–reply: one message per turn. The flags change that. "The low 16 bits declare what the current message contains, and what the expectations of the recipient are." Unknown low bits are an error, and unknown high bits are ignored.OP_MSG spec mongod 8.0 knows exactly three, and rejects any other bit in the low 16 with IllegalOpMsgFlag.op_msg.hop_msg.cpp

BitNameBytesMeans
0checksumPresent01 00 00 00The last 4 bytes are a CRC-32C of everything before them.
1moreToCome02 00 00 00On a request: "don't reply". On a reply: "another reply follows".
16exhaustAllowed00 00 01 00On a request: "I can take many replies." (optional bit)

2a · moreToCome on a request: the w: 0 insert

One example, step by step. pymongo inserts one review with WriteConcern(w=0), then inserts it again with the same _id.

0.001s c>s len=250  id=1957747793 re=0  OP_MSG flags=[moreToCome] insert body 76 B · seq 'documents' 152 B, 1 docs (138–138 B)
0.001s c>s len=250  id=424238335  re=0  OP_MSG flags=[moreToCome] insert body 76 B · seq 'documents' 152 B, 1 docs (138–138 B)
c>s: 2 messages, 500 bytes on the wire
s>c: 0 messages, 0 bytes on the wire
  1. The driver sets moreToCome and puts writeConcern: {w: 0} in the body. The spec requires both: "Clients doing unacknowledged writes MUST set the moreToCome flag, and MUST set the writeConcern to w=0."OP_MSG spec
  2. The server runs the insert, then builds no reply. In makeCommandResponse, a moreToCome request ends with return {}; // Don't reply.service_entry_point_common.cpp The SessionWorkflow (hop 3) even asserts that it never answers a "fire-and-forget request".session_workflow.cpp
  3. The second insert fails with a duplicate key, and nobody hears it. pymongo returned acknowledged=False twice, raised nothing, and the collection held one copy. "Malformed operation or errors such as duplicate key errors are not discoverable and will be swallowed by the server."OP_MSG spec, Q&A
  4. One error is not swallowed: "not primary". The server throws NotWritablePrimary, which closes the connection, "to get client to go through server selection again".service_entry_point_common.cpp The driver only notices the next time it uses that socket, so "at least one unacknowledged write operation will be lost".OP_MSG spec, Q&A

Notice also: the body is only 76 B because an unacknowledged write sends no lsid. No session, so no retryable write. And mongosh uses the same flag for its own cleanup: when it exits, it sends endSessions with moreToCome and doesn't wait.

2b · exhaustAllowed + moreToCome on replies: one request, many answers

The other direction. A client sets exhaustAllowed to say "I can read several replies in a row". Only then may the server set moreToCome on its replies, and it does so only for getMore and hello.OP_MSG spec Inside the server, the SessionWorkflow sends each reply and then makes up the next request itself ("synthesizes a new WorkItem"), until a reply says it's the last one.transport READMEmakeExhaustMessage

Exhaust cursor. pymongo reads the first hour of 2026-01-01 (3,600 reviews) with CursorType.EXHAUST and batch_size=1000:

0.003s c>s len=133     id=424238335 re=0          OP_MSG flags=[exhaustAllowed] getMore body 112 B
0.004s s>c len=168754  id=121       re=424238335  OP_MSG flags=[moreToCome] cursor body 168733 B
0.005s s>c len=169501  id=122       re=121        OP_MSG flags=[moreToCome] cursor body 169480 B
0.005s s>c len=101724  id=123       re=122        OP_MSG flags=[none] cursor body 101703 B
  1. One getMore goes out with exhaustAllowed (the find before it returned the first 1,000).
  2. Three replies come back with no request between them. Each responseTo is the previous reply's id (424238335 → 121 → 122), exactly as the spec says.OP_MSG spec
  3. The last reply has no moreToCome: the cursor is done. Until then, the client "MUST NOT send any more requests on this connection".

Streaming hello. You didn't ask for this one: pymongo's monitor does it on its own connection. An idle client for 25 s:

 0.001s c>s len=154  id=846930886 re=0          OP_MSG flags=[exhaustAllowed] hello body 133 B
10.015s s>c len=313  id=186       re=846930886  OP_MSG flags=[moreToCome] isWritablePrimary body 292 B
20.027s s>c len=313  id=188       re=186        OP_MSG flags=[moreToCome] isWritablePrimary body 292 B

The request carries topologyVersion and maxAwaitTimeMS: 10000. The server answers when the topology changes, or after 10 s with no change. So one request gives a reply every 10 seconds, forever, without a round trip each time. This "streaming protocol" (MongoDB 4.4+) is how drivers learn of a failover right away instead of at the next poll.server monitoring spec Lesson 7 covers the monitor's side of this.

2c · checksumPresent: a CRC-32C nobody in your app sends

Drivers don't set it. To see it, the lab builds a ping by hand in Python with flagBits = 1 and a CRC-32C at the end:

0.000s c>s len=55  id=901 re=0    OP_MSG flags=[checksumPresent] ping body 30 B · CRC-32C ok
0.000s s>c len=42  id=125 re=901  OP_MSG flags=[checksumPresent] ok body 17 B · CRC-32C ok
0.001s c>s len=55  id=900 re=0    OP_MSG flags=[checksumPresent] ping body 30 B · CRC-32C MISMATCH
                                  (no reply: the server closed the connection)
  • The reply has a checksum because the request had one, and only on a non-TLS connection.session_workflow.cpp mongod computes it with WiredTiger's CRC-32C function.op_msg.cpp
  • A wrong CRC kills the connection. The log said ChecksumMismatch: OP_MSG checksum does not match contents.op_msg.cpp
  • Who uses it? mongod and mongos, among themselves, when they don't use TLS. With TLS they skip it, because TLS already protects the bytes.wire protocol (9.0)

Answer to warm-up question 2: 00 00 00 00 meant "no checksum at the end" and "I want a reply" (no moreToCome), and also "only one reply, please" (no exhaustAllowed).

3 · Kind 1: a thousand reviews without an array

A kind 1 section is a document sequence: an int32 size, a name (cstring), then BSON documents "back to back with no separators". The name is the body field it replaces, and that field "MUST NOT also exist in the body".wire protocol (9.0) The server accepts it for three arguments only: insert.documents, update.updates, delete.deletes.OP_MSG spec

One example: insertMany of 1,000 reviews

The same 1,000 seed reviews (without _id, so the driver makes new ones), sent by two drivers:

# pymongo 4.19
0.005s c>s len=164256  id=1649760492 re=0  OP_MSG flags=[none] insert body 86 B · seq 'documents' 164148 B, 1000 docs (125–212 B)
0.016s s>c len=45      id=83 re=1649760492 OP_MSG flags=[none] n body 24 B
# mongosh 2.13 (Node driver 7.5.0)
0.087s c>s len=169147  id=15 re=0          OP_MSG flags=[none] insert body 169126 B
0.098s s>c len=45      id=108 re=15        OP_MSG flags=[none] n body 24 B
  1. pymongo splits the command in two sections. A kind 0 body of 86 B: {insert: "scratch", ordered: true, lsid, $db: "store"}. Then a kind 1 section named documents: 4 B size + documents\0 (10 B) + 1,000 reviews = 164,148 B. Total 16 + 4 + 1 + 86 + 1 + 164,148 = 164,256 B.
  2. mongosh puts the reviews in the body, as one BSON array documents: [ … ] of 169,029 B. The spec says bulk writes "SHOULD use Payload Type 1, and MUST do so when the batch contains more than one entry"OP_MSG spec, but this Node driver version didn't (the same spec text, in its current form). Both work: the server treats the two forms the same.
  3. The difference is the array keys. A BSON array is a document whose keys are "0", "1", … "999". Each element costs a type byte, the key, and a NUL: 1,000 + 2,890 + 1,000 = 4,890 B. That's the whole gap (169,029 = 4 + 4,890 + 164,134 + 1). About 3% here, on 164-byte reviews.
  4. One reply for 1,000 reviews: 45 B, {n: 1000, ok: 1}. Compare lesson 6: one review cost a 483 B request and a 230 B reply.

The bytes saved are small. The bigger point of kind 1 is the limit it avoids, as the next example shows.

The three limits, and how drivers split a batch

The server announces them in every hello reply. The lab's values:

  • pymongo stops at 100,000, maxWriteBatchSize. Its sequence is 16,434,499 B, bigger than 16 MiB, and that's allowed: in a sequence the 16 MiB limit is per document. Only the 48 MB message limit applies to the whole.
  • mongosh stops just under 16 MiB, because its array lives inside the body, and the body is one BSON document. With bigger documents (≈ 500 B or more), kind 1 would also be the one that packs more per message: up to 48 MB instead of 16 MiB.
  • The split is invisible to you. Both drivers sent three commands and returned one result with 250,000 ids. On this laptop both took 1.3–1.75 s.

The 8.0 parser also allows at most two sequences per message, and rejects a name that's also in the body.op_msg.cpp (There is also a kind 2, a security token for server-internal use only, and the 9.0 spec adds a kind 3 for telemetry, which 8.0 doesn't accept.)

4 · OP_COMPRESSED: the same message, smaller

OP_COMPRESSED keeps the 16-byte header (with opCode 2012) and adds 9 bytes: originalOpcode (int32), uncompressedSize (int32, without the header), compressorId (uint8: 0 noop, 1 snappy, 2 zlib, 3 zstd). Then the compressed bytes of everything after the original header.compression specCompressionHeadercompressor ids So flagBits and sections are hidden inside. The parser decompresses them to show you.

One example: a client with compressors=snappy

  1. Handshake, uncompressed. The driver's first command is the handshake hello (pymongo sends it as legacy ismaster), with compression: ["snappy"]. The server replies with the names it also supports, in the client's order: compression: ["snappy"].serverNegotiate mongod 8.0 supports snappy,zstd,zlib by default (net.compression.compressors).options IDL
  2. The client picks "the first compressor in the client's configured compressors list that is also in the servers list", and compresses every request with it.compression spec
  3. Except a fixed list, never compressed: hello and legacy hello, saslStart, saslContinue, getnonce, authenticate, createUser, updateUser (and old copydb* commands), "to mitigate against current and previous attacks".compression spec In the capture, the handshake and the monitor's streaming hello stayed plain OP_MSG.
  4. The server answers in kind. It decompresses a request, remembers its compressorId, and compresses the reply with the same one. A plain request gets a plain reply.session_workflow.cpp If the compressed buffer could exceed 48 MB, it sends the message uncompressed.compressMessage
0.769s s>c len=346      … OP_MSG flags=[none] … (handshake reply, contains compression: ['snappy'])
0.771s s>c len=4752     … OP_COMPRESSED(snappy) originalOpcode=2013 uncompressedSize=16965 → 16981 B inside: OP_MSG … cursor
0.866s s>c len=3364424  … OP_COMPRESSED(snappy) originalOpcode=2013 uncompressedSize=14776124 → 14776140 B inside: OP_MSG … cursor

How much it saves on reviews, and what it costs

The test: read one day of reviews, find({_id: {$gte: ObjectId(2026-01-01), $lt: ObjectId(2026-01-02)}}), which is 86,400 reviews. That's two replies: the first batch of 101 reviews (16,981 B), and one getMore with the other 86,299 (14,776,140 B, under the 16 MiB batch limit). pymongo, best of 3 runs, two lab runs each.

compressors=Bytes on the wireRatioSame host100 Mbit/s + 20 ms
(none)14,793,1211.0×158–182 ms1,437–1,441 ms
snappy3,369,1764.4×174–188 ms491–501 ms
zstd2,086,9477.1×185–214 ms397–431 ms
zlib1,625,8449.1×391–426 ms578–609 ms
  • On a fast link, compression only costs. Same host, the network is not the bottleneck: snappy and zstd were a little slower, zlib more than twice as slow. CPU is spent on both sides.
  • On a slow link, it wins big. I limited mongod's outgoing traffic with tc netem to 100 Mbit/s plus 20 ms delay, a rough stand-in for a cross-region link. 14.8 MB then takes ~1.2 s just to transmit. zstd cut the read from 1.44 s to about 0.4 s. It had the best balance: almost zlib's ratio at a fraction of its CPU. mongod uses zstd's default level and zlib's default level (6).zstdzlib
  • The seed reviews are very repetitive (24 sentence pieces, 10 tags), so they compress unusually well. Real review text will compress less. Measure your own ratio: serverStatus().network.compression.<name>.compressor.bytesIn / bytesOut. In the lab it gave 4.39 / 7.09 / 9.10, the same as the capture. And network.physicalBytesOut (on the wire) vs network.bytesOut (before compression) shows the total effect.serverStatus

5 · Read the wire in the source

All at tag r8.0.34, the lab's version. About ten minutes.

  1. rpc/op_msg.cpp L152–257: OpMsg::parse. Find the flag check, the switch on section kind, the "at most 2 sequences" rule, and the checksum check at the end.
  2. db/service_entry_point_common.cpp L2299–2332: makeCommandResponse. moreToCome → no reply; exhaustAllowed → ask the command whether to run again.
  3. transport/session_workflow.cpp L321–363: makeExhaustMessage builds the synthetic next request and sets moreToCome on the reply. Then L624–641: decompress the request, compress the reply with the same compressor.
  4. transport/message_compressor_manager.cpp L72–124: compressMessage writes the 9-byte header and the compressed bytes.

6 · So in production you should…

Rule: send writes in batches, turn on zstd compression where the network is the bottleneck (not everywhere), and never use w: 0 for data you'd miss.

  1. Batch writes with insertMany / bulkWrite, and let the driver split. 1,000 reviews cost one 164 KB message and one 45 B reply, not 1,000 round trips. The driver already splits at 100,000 operations, 16 MiB or 48 MB. Your own batch size is about latency and memory: a few thousand small documents per call is a good start. Each batch is still one command on one connection (hop 3), so a huge one holds that connection for its whole run.
  2. Turn on compression for cross-region or cross-AZ traffic and for big reads (exports, analytics, large result batches), with ?compressors=zstd,snappy in the connection string. On a fast, same-zone link it only adds CPU. Check the effect with network.compression counters and physicalBytesOut. Cross-AZ and cross-region bytes are usually billed, so a 4–7× ratio can matter for cost as well as speed.
  3. Prefer zstd; use snappy when CPU is tight. In the lab zstd got 7.1× for about the CPU of snappy's 4.4×. zlib squeezed most but was the slowest everywhere. Remember the driver must ship the library: mongosh 2.13 in the mongo:8.0 image only had zlib, and pymongo needed extra packages for zstd and snappy.
  4. Know what w: 0 gives up. You get no reply, so: no errors (a duplicate _id or a validation failure just vanishes), no write count, no retryable write (no lsid), and on a failover at least one write is silently lost before the driver notices. What you save is one round trip. A batched w: 1 write saves almost as much and tells you what happened.
  5. Leave the other flags to the driver. Streaming hello (exhaust) is on by default and is why failover detection is fast. Exhaust cursors pin a connection until the stream ends. Checksums are for mongod-to-mongod traffic without TLS; use TLS instead.
