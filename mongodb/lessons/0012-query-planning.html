Query planning and the plan cache

What happens inside workingMillis, before the first page is read: how the server picks one index out of several, remembers its choice, and notices when the choice has gone stale.

Your win today: given a slow-log line for a reviews query, you can say which index was chosen and why, whether that plan came from the cache, whether it was replanned, and what to do about it (a better index, a hint, or nothing).

1 · From filter to plan, step by step

The query: "verified reviews with 4★ or more, about the battery".

db.reviews.find({ verified: true, rating: { $gte: 4 }, tags: "battery" })

The collection has three secondary indexes: {verified: 1, rating: 1}, {rating: 1} and {tags: 1} (multikey), plus _id. The server's query code is documented in its query README. In order:

Step by step: the race (step ⑤)

With three plausible indexes, the server doesn't guess from statistics. It runs all candidates at the same time, taking turns one unit of work at a time (one "work" is one step of a plan stage: advance an index cursor, fetch a document), and stops when one plan returns a first batch of 101 results, or any plan reaches the end. The trial is capped at max(10000, 0.3 × documents) works (internalQueryPlanEvaluationWorks and …CollFraction).multi_plan.cpp Then the plans are ranked by results produced per work.

This is what explain("allPlansExecution") showed on 500,000 reviews:

CandidateWorksResults returnedResult
{tags: 1}195101winner (first full batch)
{verified: 1, rating: 1}19542rejected
{rating: 1}19529rejected

Why did tags win? Each work on the tag index lands on a review for which the other two predicates hold more often. In the trial, it turned 195 works into 101 matches, the other two into 42 and 29. The full query then returned 45,902 reviews after 93,748 keys and documents (55 ms). Note what the trial measures: progress per work on the first 101 results, not total cost.

2 · The plan cache: remember the winner

Racing three plans costs real work on every execution. So the server stores the winner, keyed by the query's shape: the filter, sort and projection with the constants removed.query README: plan caching The cache lives in memory on each mongod (never on mongos) and is lost on restart.

Step by step, same query, run four times on a fresh cache ($planCacheStats):

  1. Run 1: multi-planning. An entry appears: isActive: false, works: 195, index tags_1. An inactive entry exists but isn't used yet.
  2. Run 2: same shape, multi-planned again (the entry is inactive). Its trial is as good as the entry's, so the entry becomes isActive: true.
  3. Runs 3–4: the plan comes from the cache. No race. explain() now shows isCached: true.

Why the two-step? The query README: an unreasonably high works value in a new entry would never trigger replanning, so an entry is only trusted once a second trial matches or beats it.inactive entries

Constants don't matter: {verified: false, rating: {$gte: 2}, tags: "price"} maps to the same entry (still one entry in the cache). Changing the shape does: tags: {$in: [...]} made a second entry.

There are two caches. The classic engine has one cache per collection and stores index choices ("tags"); the plan tree is rebuilt on each use, and a query with only one candidate gets no entry. The SBE cache is one per process and stores compiled, auto-parameterized plans, so even single-candidate queries are cached.query README Any index build or drop, or collection drop, clears the collection's entries.

3 · Replanning: noticing a stale choice

A plan that was best for one set of constants can be terrible for another. The cache handles this with a trial on every cache hit: run the cached plan for up to 10 × works (internalQueryCacheEvictionRatio) until the first batch is ready. If it needs more, the buffered results are thrown away, the entry is deactivated, and the query is planned from scratch.cached_plan.cpp L104

I built a case with one shape and very different constants. The only change is how far back the _id range reaches (_id encodes the time, from lesson 2):

{ _id: { $gte: X }, rating: 1, verified: false, tags: "sound" }
  1. Narrow (X = the last 100 reviews): the _id index wins, 100 keys, 0 results, works: 101. Run three times, it is active and fromPlanCache: true.
  2. Wide (X = the first review, same shape): the cached plan is the _id scan. To find 101 matches in a 0.6%-selective filter it would need thousands of works, but the cap is 10 × 101 = 1,010. The profiler says: 
    "replanned": true, "replanReason": "cached plan was less efficient than expected:
  expected trial execution to take 101 works but it took at least 1010 works"
planSummary: IXSCAN { verified: 1, rating: 1 }   keysExamined: 556
  3. The new winner is cached, as inactive with works: 202, then 404, then 808 on the next runs. Every replan that doesn't confirm it doubles the stored works, so the entry gets room to settle.

Replanning is a safety net, not an optimizer. In a milder case ({_id: {$gte: X}, rating: 5}) the narrow plan was cached, and the wide query ran the _id scan 3 times at ~775 ms with no replan: it found its 101 results well within 1,010 works. Starting fresh, the planner chose {rating: 1} and took ~650 ms. A plan that is 20% worse but never crosses the 10× line stays cached forever.

4 · Two engines: classic and SBE

MongoDB 8.0 has two execution engines. The classic engine interprets a tree of stages (IXSCAN, FETCH, …) one document at a time. The slot-based engine (SBE) compiles the plan into a tree of stages that pass values in numbered slots. It was designed to run queries that span several collections (for example $lookup), and it has its own, process-wide plan cache.query README The default internalQueryFrameworkControl is trySbeRestricted: SBE only for query shapes where it is known to help.

You can tell which ran: queryFramework in the slow log (we saw "sbe" for the countDocuments in lesson 10), or explainVersion. On this data a plain find with an index stayed classic (explainVersion: 1, FETCH over IXSCAN), while aggregate([{$match…}, {$group: {_id: "$rating", …}}]) used SBE (explainVersion: 2). Indexes work the same in both; only the executor and the cache differ.

7 · So in production you should…

Rule: make the right index obviously best, so the race and the cache have nothing to get wrong. Give each important query one index that matches its equality fields first, then its range, then its sort.

  1. Read planCacheKey, queryHash and replanned in the slow log. replanned: true repeating for one shape means one plan doesn't suit all its constants.
  2. Don't depend on the trial. It picks the plan that makes quick progress on the first 101 results. With a sort or a big result set, that can differ from the plan with the lowest total cost. A compound index that serves filter and sort removes the contest.
  3. Skewed values are the classic trap (one tag with 80% of reviews, one with 0.1%). Either split the query by value in application code, or use a hint or Query Settings (setQuerySettings, 8.0) to pin the index for that shape.
  4. After index changes, expect a short spike. Building or dropping an index clears that collection's cache entries; every shape is multi-planned again (planCacheKey stays the same, fromPlanCache is absent for the first runs).
  5. Too many indexes make the race longer and noisier. Each extra candidate means more trial work and more chance of a surprising winner. Drop indexes nothing uses ($indexStats).
  6. Check the cache when a query suddenly changes: db.reviews.getPlanCache().list() or $planCacheStats; getPlanCache().clear() forces fresh planning.
