MongoDB Internals · Lesson 0007 · Phase 2: Transport & wire

The driver's side: pool and monitoring

Before mongod sees a single byte of your query, the driver has already done three things: it knew which servers exist, it picked one, and it borrowed a connection. This lesson opens hop 1.

Your win today: when your app sees a slow find but the server's durationMillis is short, you can prove the time went into the driver's wait queue, and you can choose maxPoolSize, maxConnecting and the timeouts with a reason for each. That's the "diagnose a production symptom by naming the mechanism and the metric" goal from your mission.

1 · What one MongoClient holds

Our query, as always: db.reviews.find({rating: {$gte: 4}}) in store.reviews. The app talks to a 3-member replica set (m1 primary, m2, m3). Inside the MongoClient there are three parts. Each one has its own driver spec, which every official driver implements:

  • Monitoring (SDAM). One monitor per server keeps the client's picture of the cluster, the topology description: who is primary, who is a secondary, how far away each one is.server monitoring spec
  • Server selection. For each operation, it uses that picture and your read preference to choose one server.server selection spec
  • Connection pool (CMAP). One pool per server. The operation borrows ("checks out") a connection, uses it for one command, and gives it back ("checks in").CMAP spec

2 · The walkthrough: one find through hop 1

Measured with the Node.js driver 7.7.0 (current release, 2026-09) and mongo:8.0 (8.0.34), a 3-node replica set in Docker, 200,000 seeded reviews. Defaults are from the driver's own source at tag v7.7.0.connection_string.ts

  1. The picture is already there. When the client started, the monitors connected to every host in the URI and ran hello. The replies said "I'm primary" or "I'm secondary", and the client built its topology description from them. Your find does not wait for that again.
  2. Server selection. The default read preference is primary, so only m1 is suitable. With secondaryPreferred or nearest there can be several suitable servers; section 3 shows how it picks one. If no suitable server exists (say, during an election), the driver asks the monitors for an immediate check and waits, up to serverSelectionTimeoutMS = 30 s.selection loop
  3. Check out from m1's pool. Three cases, checked in this order:processWaitQueue
    • an idle connection is in the pool → take it (fast path, microseconds);
    • fewer than maxPoolSize (100) connections exist and fewer than maxConnecting (2) are being opened right now → open a new one;
    • otherwise → wait in the wait queue, in order, until a connection is checked in.CMAP WaitQueue
  4. Opening a connection (only if needed) is several round trips: TCP connect, the TLS handshake if TLS is on, then the MongoDB handshake. The handshake is one hello carrying your client metadata, and with credentials it also carries the first step of SCRAM authentication (speculativeAuthenticate), which saves one round trip.connect.tsscram.ts In the lab, a new connection was ready in 1 ms (p50) without auth and 1–2 ms with SCRAM-SHA-256. The first authenticated connection in a process took 7–9 ms: the driver caches the expensive salted-password step after that.HI cache (TLS I did not measure. Across a real network, every one of these round trips costs your RTT.)
  5. Send, wait, check in. The find goes out as one OP_MSG (hop 2, next lesson) on that connection. The connection is now busy until the reply comes back. Then it goes back to the pool for the next operation.

The server sees the handshake too. $currentOp shows each connection's clientMetadata, which is where appName comes from:

{ desc: 'conn185', client: '172.19.0.6:33482',

3 · Monitoring and selection: the sockets you didn't ask for

The lab's monitor experiment ran one findOne, waited 25 s, and then asked each member's $currentOp (with idleConnections: true) for sockets with our appName:

MemberActiveCommandWhat it is
m1truehello, maxAwaitTimeMS: 10000monitor: a streaming hello, parked on the server
m1false(idle)RTT pinger
m1false(idle)the pooled connection our findOne used
m2true / falsehello / (idle)monitor + RTT pinger
m3true / falsehello / (idle)monitor + RTT pinger
  • Streaming monitor. The monitor sends hello with its last topologyVersion and maxAwaitTimeMS = heartbeatFrequencyMS (10 s). The server holds the request and answers when its state changes, or when the 10 s run out. With the exhaustAllowed flag it can keep answering without new requests (that's OP_MSG's moreToCome, lesson 8).streaming protocolmonitor.ts In the lab the heartbeats per member arrived at +14 ms, +10.5 s and +20.5 s. So a step-down reaches the client in milliseconds, not in "up to 10 s".
  • RTT pinger. A parked hello can't measure latency, so streaming needs "an extra thread and an extra socket for each monitor to perform RTT calculations." The client keeps the minimum and average over the last 10 samples.measuring RTT (On FaaS platforms like Lambda, serverMonitoringMode: "auto" switches to polling, with no RTT socket.)
  • Not in the pool, no auth. Monitoring uses "a dedicated socket that does not count toward the pool's maximum size", and drivers "MUST NOT authenticate on sockets used for monitoring".dedicated socketsmonitor.ts So the server's real count per app process is 2 × members + pool sizes.
  • When a check fails with a network error, the monitor marks the server Unknown and clears its pool, then checks again at once.SDAM error handling A network error on an application connection does the same.

Choosing among several servers: the latency window

With nearest (or several eligible secondaries), selection is: take the suitable servers, keep those whose RTT is within localThresholdMS (15 ms) of the fastest one, then pick two of them at random and use the one with fewer operations in flight.latency windowtopology.ts In the lab, all RTTs were 0–5 ms, so all three members were in the window and each got about a third of 3,000 finds (960–1,033). With localThresholdMS: 0, the finds went to whichever one or two members tied for the lowest RTT.

4 · The pool under load

To make the server work, the lab uses the slow version of our query: positive reviews that mention a refund, find({rating: {$gte: 4}, review: /refund/}). No review says "refund", so every run scans all 200,000 documents and returns nothing. Alone, it takes 74–77 ms (executionTimeMillis). Then: 40 of them at once, for different maxPoolSize values. The driver's CMAP events give the checkout wait (ConnectionCheckedOut.durationMS), command monitoring gives the command time, and the server's slow-query log gives durationMillis. That's the symptom from your win: the server's slow log said durationMillis ≈ 103 ms, and the app saw ~550 ms. 80% of the latency was the wait queue, and the server can't see it: at +300 ms, $currentOp showed 5 finds while 25 more were queued in the driver. The answer to warm-up question 2: the last one took about 0.9 s, roughly 40 ÷ 5 = 8 rounds of ~110 ms.

Now the surprise. With 40 connections, the driver wait went away, but the command time grew to ~600 ms, and the total hardly moved. The slow log shows where: durationMillis ~585 ms, workingMillis ~170 ms, and queues.execution.totalTimeQueuedMicros ≈ 500,000–640,000. The finds were waiting for an execution ticket inside mongod (8.0's throughput-probing admission control limits how many operations run in the storage engine at once).execution control README CPU per find (cpuNanos) was ~95–125 ms either way.

A bigger pool doesn't create capacity. It moves the queue. With 5 connections the queue is in your driver, invisible to the server. With 40 it's in mongod's admission queue, visible in the slow log as durationMillis − workingMillis. The work is the same 40 collection scans. The fix for this query is an index, not a pool size. Lessons 9 and 10 go inside mongod's side of this.

How long does a request wait for a connection?

In Node 7.7.0, waitQueueTimeoutMS defaults to 0, which means no limit. Without timeoutMS, the checkout has no timeout at all.timeout.ts With timeoutMS set (client-side operation timeout, the spec's replacement for waitQueueTimeoutMS), the checkout counts against the same budget as server selection.CMAP optionstimeout.ts With maxPoolSize: 5, waitQueueTimeoutMS: 200, the same 40 finds gave 10–14 ok and 26–30 MongoWaitQueueTimeoutError. That's what you want: a fast, explicit "pool exhausted" error instead of a request that hangs.

5 · Connection storms: maxConnecting and failovers

A cold pool and a burst of work is the moment a pool can hurt the server. maxConnecting (default 2) is the number of connections one pool may be opening at the same time.connection_pool.ts The lab fired 100 fast finds (find({rating: {$gte: 4}}).limit(1)) at a brand-new client:

maxConnectingconnections openedsetup time, p50app sees, p50all 100 done
2 (default)11–136–8 ms29–42 ms42–63 ms
103116 ms45 ms61 ms
10010035–62 ms60–98 ms76–108 ms

With 2 at a time, connections finished and were reused before the driver needed more: 100 finds were served by ~12 connections. With 100 at a time, the client opened 100 connections, each one took about 5–10× longer to set up, and the burst finished later. Each connection costs the server too: on 8.0 a new connection gets its own thread (lesson 9).

  • A step-down doesn't close client connections, and the stepped-down primary nominates a secondary to call an election immediately.replSetStepDown The driver only clears a pool for "node is shutting down" errors, not for "not writable primary".SDAM So when m1 took over again 10 s later (it has priority 2), its 20 connections were still there.
  • A crash costs the election timeout. Nobody nominates anyone. The secondaries wait electionTimeoutMillis (10 s by default) before they call an election.elections There were no errors because every find sat in server selection (step 2) waiting for a primary, and that wait is allowed up to 30 s. To your app it looks like a 10.8 s query.
  • The storm. Each process opened its pool to the new primary right away. Here that was 20 connections from one process. With 50 app instances at maxPoolSize: 100, that's up to 5,000 new connections (with SCRAM and maybe TLS) hitting one mongod in the seconds after an election, on top of the 2 monitoring sockets each process keeps on every member (100 per member for 50 instances). Deploying 50 instances at once creates the same wave. maxConnecting slows each process's share of it.

6 · So in production you should…

Rule: measure the checkout wait in the driver, size the pool for the concurrency the server can actually run, and give every request a time budget, so pool exhaustion fails fast instead of looking like a slow query.

  1. Subscribe to CMAP events (or your APM's equivalent) and graph checkout wait next to command time. connectionCheckedOut.durationMS is the number the server will never show you. Set appName on every client so its connections can be found in $currentOp and the slow log.
  2. Don't fix latency by raising maxPoolSize unless the server is idle. If durationMillis − workingMillis grows when you raise it, you moved the queue into mongod. Fix the query (here: an index), or add capacity.
  3. Set timeoutMS (or at least waitQueueTimeoutMS). The Node default waits for a connection forever. A bounded wait turns a hidden pile-up into an error you can count and alert on.
  4. Leave maxConnecting at 2 unless you've measured that warm-up is too slow. Raising it made the burst slower, not faster.
  5. Do the connection math for the whole fleet: instances × (pool in use + 2 per member). Compare it with serverStatus().connections on the primary, and expect the pool part to arrive all at once after a failover or a deploy. A minPoolSize keeps a warm pool, but on every member, so it also adds idle connections.CMAP rationale
  6. Prefer planned step-downs (rolling maintenance) over killing a primary: 30 ms vs. 10.8 s in the lab. And remember that a step-down kills writes that are in progress; retryable writes cover one retry.replSetStepDown

Where this fits

  1. Hop 1, the driver: pool, monitoring, server selection (today)
  2. Hop 2, the wire: OP_MSG in depth: flag bits (moreToCome, exhaustAllowed, which the streaming hello uses), document sequences, compression
  3. Hop 3, transport: server ingress: what each of those connections costs mongod
  4. Hop 4, dispatch: command dispatch and interruption: maxTimeMS, killOp, currentOp
  5. Recap: diagnose a latency spike across hops 1–4

Read the Connection Monitoring and Pooling spec: the "Connection Pool Behaviors" section (checkout, wait queue, clearing) and the event list. Then the Server Monitoring spec: "Streaming protocol" and "Measuring RTT". Every official driver implements these, so what you learn transfers from Node to Java or Python. To see one implementation, open processWaitQueue in the Node driver (v7.7.0). It's 90 lines.
