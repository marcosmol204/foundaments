Sharding: routing, shard keys and the balancer

How mongos decides which shard gets a review, why the shard key decides almost everything, and what the balancer does (and doesn't) to even things out.

Your win today: given a shard key for store.reviews, you can predict which queries hit one shard and which hit all, whether new reviews spread or pile onto one shard, and read the balancer's state from config.chunks.

1 · The pieces

  • A shard key is a field (or fields) of every document. The collection is cut into contiguous chunks of the key's value range, each owned by exactly one shard. The map is config.chunks.
  • mongos is stateless apart from a cache of that map. It parses a command, finds the owning shards from the key in the filter, forwards it, and merges results. It has no data and no oplog.
  • The router and shard roles are in the server source's sharding guide (src/mongo/db/s/README.md), which also lists the balancer, migrations and the range deleter as the main parts.sharding README

2 · Routing: one shard or all of them

I loaded 200,000 reviews and sharded them on {_id: "hashed"} across 2 shards. Then I ran explain("executionStats") through mongos:

QueryStageShards askedDocs examined
find({_id: id})SINGLE_SHARD1 (s2rs)1
find({_id: {$gte: X}}) (a range of 10,000)SHARD_MERGEboth10,000
find({rating: 5, verified: true})SHARD_MERGEboth295,880 (COLLSCAN on each)
find({tags: "battery"}).limit(10)SHARD_MERGEboth111 total (stops early)
  1. Equality on the shard key → one shard. mongos hashes the _id, finds the chunk, asks one shard. This scales: more shards, same cost.
  2. A range on a hashed key → every shard. Hashing scatters neighbouring values; a range of consecutive _ids (which means "reviews in a time window") lives everywhere. With a ranged key the same filter would hit the one or two shards owning that range.
  3. No shard key in the filter → scatter-gather. Every shard works, mongos merges (and sorts, if asked). The cost is the sum, and the slowest shard sets the latency. The lab query read 295,880 documents with no index on rating.

That last number is larger than the 200,000 reviews. Shard s1rs had 200,000 documents on disk while owning only half: after a migration, the donor keeps the moved documents (orphans) until the range deleter removes them, by default after a delay. Queries filter orphans out, but they still pay to read them: a COLLSCAN read 200,000 on s1rs plus 95,880 on s2rs. Counts through mongos are correct (200,000); $collStats per shard are not.migrations README

How does mongos know its cached map is right? Every request carries the version of the routing info it used; a shard that owns a different version answers with a stale-config error and mongos refreshes from the config servers and retries. I didn't trigger that here; it's described in the README on versioning protocols.sharding README

3 · The shard key decides where writes go

Each experiment: an empty sharded store.reviews, then 60,000 new reviews inserted in order (their _ids grow with time, like real ones). I counted inserts handled by each shard (opcounters.insert):

Shard keys1rs insertss2rs insertsWhy
{_id: "hashed"}30,03829,962The hash spreads consecutive ids evenly.
{_id: 1} (ranged)60,0000Every new _id is above all existing ones, so every insert goes into the last chunk, on one shard.

That is the hot shard problem for monotonically increasing keys (ObjectIds, timestamps). The balancer can move old chunks away afterwards, but the chunk taking new writes is always the top one; it can only be split, and the new top chunk lands on the same shard.

A third key shows the opposite failure. With {rating: 1} (five values) and a range size of 1 MB (I shrank it, to see in seconds what 128 MB shows at scale), all 120,000 reviews stayed on one shard:

chunk {rating: MinKey} -> {rating: 3}   s1rs JUMBO
chunk {rating: 3}      -> {rating: 4}   s1rs JUMBO
chunk {rating: 4}      -> {rating: 5}   s1rs JUMBO
chunk {rating: 5}      -> {rating: MaxKey} s1rs JUMBO
rating 2: 12,000 · 3: 12,000 · 4: 36,000 · 5: 60,000

A chunk can be split only between key values. With five values there are at most five chunks, and the one holding 5★ (60,000 reviews) can never be split further. Chunks above the range size that can't be split are flagged jumbo and are not moved. A shard key needs high cardinality (many distinct values) and a good spread of both data and writes.

Which of the course's fields could work? _id: "hashed" spreads writes and data and gives targeted _id lookups. {verified: 1, rating: 1} has only 10 combinations: too few. A compound key such as {rating: 1, _id: 1} adds cardinality, but still sends all new 5★ reviews to one end of one range. The shard key you want is the field most queries filter on that also has many values; for a review store that usually points at a product id, which this collection lacks (I'm only noting it: the schema stays as it is).

4 · The balancer, step by step

The balancer is a background thread on the config server's primary. In rounds with a pause between them, it first splits oversized ranges, then moves ranges from the shard with the most data to the one with the least.balancer README I sharded the 200,000 loaded reviews on {_id: "hashed"}, so everything began on s1rs (31 MB, one chunk), and shrank the range size to 1 MB to make it act:

  1. ≈5 s: still 1 chunk on s1rs. The balancer's first round is a delay away.
  2. 10–25 s: the range was split into 16 chunks and 15 of them moved to s2rs, one migration at a time: 5, 9, 13, 15 chunks on s2rs. Each migration went through the 6 steps in config.changelog (moveChunk.start → commit). The slow step is step 4 (about 106 ms of the ~165 ms in the one I read), where the data is cloned and the recipient catches up.
  3. Then it stopped, with balancerCompliant: true, even though the chunk counts read s1rs: 1, s2rs: 15. Real documents: s2rs 95,880 and s1rs about 104,000. Since 6.0 the balancer balances by data size, not chunk count, so one big chunk on s1rs and fifteen small ones on s2rs are already even.
  4. Moved documents stayed on s1rs as orphans (raw count 200,000) until the range deleter ran.

A migration, from the README: the recipient clones the range while the donor keeps serving; then the donor enters a critical section that blocks writes (and then reads) to that range, the recipient catches up, the ownership change is committed on the config servers, and the critical section is released.migrations README It's short, but it exists: writes to that range wait during it, and migrating costs I/O and cache on both shards (lessons 3 and 5).

7 · So in production you should…

Rule: choose the shard key from your queries and your write pattern, not from the data's shape. It should appear in the filter of your hot queries, have many values, and not increase monotonically. It is hard to change later.

  1. Put the shard key in every hot query. One shard answers; the rest don't work. Everything else is scatter-gather, whose latency is the slowest shard's.
  2. Don't use a monotonically increasing key as a ranged key (the 60,000 / 0 split in the lab). Hash it, or lead with a high-cardinality field.
  3. Avoid low-cardinality keys (rating, verified): chunks can't split below one value and become jumbo. Compound them with something high-cardinality.
  4. Hashed keys trade away range queries. Time-window queries on _id hit every shard. If those matter, shard on a ranged key that includes another prefix.
  5. Don't trust per-shard counts after migrations. Orphans inflate $collStats and scans; count through mongos, and let the range deleter finish before measuring.
  6. Judge balance by data size and load per shard, not chunk counts. sh.status(), getShardDistribution() and the balancer window setting (to keep migrations out of peak hours) are your tools.
  7. You can change the key later with reshardCollection (5.0+), but it copies the whole collection. Treat the choice as a design decision, and test it with the shard key analyzer before you shard.
