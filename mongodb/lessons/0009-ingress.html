Server ingress: threads and sessions

Hop 3 from lesson 6. What mongod does when a connection arrives, which thread runs it, and what each idle connection in your app's pool costs the server.

Your win today: given "N app instances, pool size P", predict how many threads and how much memory a mongod spends on them, say what happens when the limit is hit, and name the serverStatus fields that prove it. Every number in this lesson was measured on mongo:8.0 (8.0.34) in Docker, with -m 1g and 10,000 seeded reviews.

1 · One connection, step by step

We follow one connection from the lab: number 38, from a small client that does what a driver does on a new pooled connection. It sends hello with client metadata, runs db.reviews.find({rating: {$gte: 4}}).limit(1), and then sits idle, like most connections in a real pool.

  1. Accept. A single thread named listener accepts TCP connections and hands each new socket, wrapped in a Session, to the session manager.asio_transport_layer.cpp "Once a client connection is accepted, a Session object is created to manage it."transport README
  2. Check the limit, then log. If the number of open sessions is already at the maximum, the server logs "Connection refused because there are too many open connections" and closes the socket. Otherwise it logs "Connection accepted" with the new connectionCount.session_manager_common.cpp Both lines come from ctx: "listener".
  3. Make a Client and a SessionWorkflow. The Client is named conn + the session id, so conn38.asio_session_manager.cpp Its thread model is always set to kSynchronous.asio_session_manager.cpp
  4. Start a dedicated thread. The synchronous executor launches a new OS thread for this client with a 1 MiB stack (kStackSize = 1024 * 1024).service_executor_utils.cpp In /proc the thread is called conn38. "For each incoming connection … a new dedicated thread is spawned then detached."command dispatch
  5. Loop: source → process → sink. Each iteration reads one message (sourceMessage), turns it into a WorkItem, passes it to handleRequest (hop 4, next lesson), and writes the reply (sinkMessage).session_workflow.cpp The code is a plain while (true), with the comment "All available service executors use dedicated threads, so it's okay to run eager futures in an ordinary loop".session_workflow.cpp When the client sends nothing, the thread blocks in sourceMessage. An idle connection is a sleeping thread.
  6. End. When the client closes the socket, sourceMessage fails, the loop ends, the server logs "Connection ended", and the thread exits.session_manager_common.cpp

Answer to warm-up 1: one. "A SessionWorkflow can only have one WorkItem in progress at a time."transport README The thread is busy for the whole command, including a w: "majority" wait.

2 · Which thread model does 8.0 use?

Old blog posts describe several thread models. In 8.0.34, the code has three service executors, and serverStatus().network.serviceExecutors shows each one:service_executor.cpp

ExecutorIn serverStatusUsed for
SynchronouspassthroughEvery client connection. One dedicated thread each. The default and, for normal clients, the only one.
ReservedreservedOnly exists if net.reservedAdminThreads is set. Used by exempt clients (section 4) when the server is already over its connection limit.service_executor_reserved.cpp
InlineinlineInternal work that runs on the caller's thread. 0 in every lab run.

There is no thread pool shared by client connections, and no async mode you can switch on. The startup parameters initialServiceExecutorUseDedicatedThread (default true) and fixedServiceExecutorThreadLimit still exist in service_executor.idl, but nothing in src/mongo/transport at 8.0.34 reads them.service_executor.idl Ignore them. The thread pools in docs/thread_pools.md are for internal and outgoing work, not for client connections.

Measured: with 3,005 connections open, passthrough.threadsRunning was 3,005 and the mongod process had 3,049 threads. That's one thread per connection plus 44 background threads (eviction, journal flusher, checkpointer, the listener…).

3 · What one idle connection costs

The lab opens 0, 1,000 and 3,000 idle connections to a fresh mongod and reads /proc/1/status (mongod is PID 1 in the official image) and serverStatus. "current" includes the 5 connections of the mongosh that takes the measurement.

Idle client connections01,0003,000
connections.current51,0053,005
connections.active111
OS threads (Threads:)48–491,048–1,0493,049
Resident memory (VmRSS)182–203 MB287–304 MB486 MB
tcmalloc current_allocated_bytes112–125 MB197–203 MB346 MB
Address space (VmSize)3.7 GB4.8 GB7.0 GB

Per idle connection, that is:

  • 1 OS thread. Exactly. Thread count tracks connections.current one for one.
  • ≈ 100 KB of resident memory (+105 MB per 1,000 on a fresh server, +303 MB per 3,000). About 78 KB of it is heap that mongod allocates (tcmalloc: the Client, buffers, per-connection state) and about 24 KB is the part of the 1 MiB stack the thread has actually touched (measured from /proc/1/smaps: 3,005 one-MiB mappings, 72 MB resident).
  • ≈ 1.1 MB of address space, mostly the reserved stack. That's virtual: it costs nothing until it's touched, but it's why VmSize looks scary.
  • 2 file descriptors: the socket, plus one so the client can be woken up (eventfd). The source says so when it computes the limit (section 4).session_manager_common.cpp

active stayed at 1. 3,000 connections, and only one of them (the measuring shell) was running anything. The other 3,000 threads were asleep in sourceMessage. That is the normal shape of a production server: many connections, few active.

The memory doesn't all come back. After the 3,000 connections closed, threads went back to 48 and tcmalloc's allocated bytes fell to 129 MB, but RSS stayed at 421 MB. tcmalloc kept the freed pages in its heap (heap_size 360 MB) for reuse. A connection spike can leave the process bigger for a long time, and that memory isn't available to the WiredTiger cache's neighbours (lesson 3).

100 KB sounds small. But 10,000 idle connections are ≈ 1 GB of RAM and 10,000 threads doing nothing. On the same box, that RAM could have been cache.

4 · The connection limit

net.maxIncomingConnections (--maxConns) is the cap. In 8.0.34 the effective limit is the smallest of three numbers:session_manager_common.cpp

  1. What you set, default 1,000,000.
  2. 80% of half the open-file limit (RLIMIT_NOFILE / 2 × 0.8): half because each connection needs two descriptors, 80% to leave room for data files. The manual lists this as the Linux default.config options In the Docker image, nofile is 1,048,576, so this gives 419,430.
  3. A memory cap (a recent addition: it's in 8.0.34; check yours with getParameter): capMemoryConsumptionForPreAuthBuffers (default 20%) of the server's memory ÷ preAuthMaximumMessageSizeBytes (16 KiB, the largest message a client may send before it authenticates).transport_options.idl With -m 1g: 1,024 MiB × 0.2 ÷ 16 KiB = 13,107. mongod read the cgroup limit, not the laptop's 7.8 GB, and said so at startup:
{"s":"W","c":"NETWORK","id":11621101,"ctx":"initandlisten",
 "msg":"Overriding max connections to honor `capMemoryConsumptionForPreAuthBuffers` settings","attr":{"limit":13107}}

So connections.available was 13,102 with 5 open. On a 64 GB server the same cap is ≈ 838,000, so you will rarely notice it, but on small containers it's real.

What happens at the limit

I started mongod with --maxConns 200 and opened 300 connections. 200 got in, 100 were refused (connections.rejected: 100), each with a log line:

{"ctx":"listener","msg":"Connection refused because there are too many open connections",
 "attr":{"remote":"172.20.0.3:37110","connectionId":205,"connectionCount":200}}

And then the important part: my own mongosh couldn't get in either (MongoServerSelectionError: connection <monitor> to 127.0.0.1:27017 closed). When the limit is full, the admin trying to diagnose it is refused like everybody else.

The fix is an exemption list. net.maxIncomingConnectionsOverride takes CIDR ranges that ignore the limit; net.reservedAdminThreads starts a small pool of threads for them. Both are config-file only and hidden from --help.server_options_general.idl Rerun with both set, 127.0.0.1/32 exempt: the client again got 200 of 300, but the local mongosh connected, and serverStatus showed connections.limitExempt: 5 and the reserved executor running.

5 · Connection storms, and the 8.0 throttles

A connection storm is many connections arriving at once: an app deploy, an autoscaler adding 20 instances, or every client reconnecting after a failover. Each new connection costs a thread, a handshake, and (in production) authentication, which is CPU-heavy. In the lab, 3,000 connections arrived in 534 ms and mongod created 3,000 threads in that half-second.

8.0.34 has three ingress throttles. Check what's on with getParameter; these are the measured defaults:

ThrottleLimitsDefault (8.0.34)

ingressConnectionEstablishment*		New connections per second; extra ones wait in a queue or are refusedOff (…RateLimiterEnabled: false), queue depth 0transport_options.idl
Ingress request rate limiter
ingressRequestAdmissionRatePerSec		Requests per second, before an operation is createdEnabled, but the rate is 2,147,483,647/s: effectively unlimitedrate limiter idl
Ingress admission control
ingressAdmissionControllerTicketPoolSize		Concurrent user operations (find, insert, …)Enabled, 1,000,000 tickets: effectively unlimitedadmission idl

The last one is the queues.ingress.admissions you saw in lesson 6's slow-query line. The manual lists the establishment limiter's serverStatus counters from 8.0.12 on, so older 8.0 patch releases may not have it.serverStatus

I turned on the establishment rate limiter at runtime at 100 connections/s, burst 1 s, queue 2,000 (with 127.0.0.1/32 in ingressConnectionEstablishmentRateLimiterBypass so my shell stayed exempt):

  • Queue depth 2,000: 1,000 connections took 9.0 s instead of 0.2 s. While they waited, connections.queuedForEstablishment showed 72, 37, 2. None were refused.
  • Queue depth 0 (the default): 123 got in, 877 were refused (establishmentRateLimit.rejected: 877). 100 is the burst, the rest are the tokens refilled during the 250 ms the attempt lasted.

One detail from the source: the rate limiter runs in the first iteration of the SessionWorkflow loop, so a queued connection already has its Session and its thread.session_workflow.cpp It smooths the CPU cost of handshakes and auth. It does not save you threads; only maxIncomingConnections does that.

6 · Sizing pools across app instances

The server's connection count is set by your apps, not by mongod. Per mongod, at most:

connections ≈ app instances × (maxPoolSize + monitoring connections)

  • The manual's example, which is warm-up 2: 4 app servers × maxPoolSize 100 = 400 incoming connections to each mongod. Each app server opens 300 in total, because it has one pool per replica set member.pool tuning
  • Monitoring adds a few per instance. Measured: one Node.js driver 6.21 client with minPoolSize=maxPoolSize=50 held 52 connections: 50 pooled plus 2 for server monitoring (lesson 7). They show up in the log with the same appName.
  • Deploys double it. During a rolling deploy, old and new instances are both connected. Plan for 2× the steady state.
  • Pools don't share. A connection waiting on one app instance can't serve a request on another. 50 instances × 100 = 5,000 threads per mongod, even if only 30 operations are ever active at once.

8 · So in production you should…

Rule: every connection is a sleeping thread and ≈ 100 KB on the server, so size pools from the server's side: add up instances × maxPoolSize (+ monitoring) for every app, keep it well under maxIncomingConnections, and always keep a way in for admins.

  1. Keep pools small and few. Most apps need far fewer connections than the default 100 per instance. Start from your real concurrency (connections.active at peak) and set maxPoolSize near it. Don't set a large minPoolSize: it keeps idle threads alive on every mongod for nothing.
  2. Set maxIncomingConnections on purpose, a bit above your computed total (with the 2× deploy margin). A limit you chose fails loudly in the log. The default fails as a memory problem.
  3. Exempt your admin and monitoring hosts with net.maxIncomingConnectionsOverride (and a couple of reservedAdminThreads). Otherwise, when connections are full, you can't connect to see why.
  4. Plan for storms. Stagger instance start-up and reconnects. If storms are a known problem (failovers, autoscaling), turn on ingressConnectionEstablishmentRateLimiterEnabled with a queue depth above 0, so connections wait instead of being refused. Exempt admin IPs with …RateLimiterBypass.
  5. Always set appName in your connection string. Then the "client metadata" lines and currentOp tell you which service is holding 3,000 connections.
  6. Container sizing: in small containers, remember the 8.0 memory cap (20% of memory ÷ 16 KiB) and that thousands of connections take RAM that would otherwise be cache.
