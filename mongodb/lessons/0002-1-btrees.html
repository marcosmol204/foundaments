B-trees, from first principles to WiredTiger

Why databases use them, a 150-line B-tree in C, and four ways WiredTiger's real B-tree differs from the textbook.

Your win today: predict when a B-tree will split and how tall it will grow. Then explain what WiredTiger does differently, and what that means in production.

Part 1 · Why B-trees?

The problem: reads come in pages

A database keeps far more data than fits in memory, so most of it lives on storage. Storage isn't read one key at a time. It's read in blocks, and each read is slow compared with working in memory. So the question for an index structure isn't "how many comparisons?" but "how many page reads per lookup?" The B-tree was invented by Bayer and McCreight (1972) to answer exactly that, for "large ordered indexes" on secondary storage.Comer 1979

Binary tree vs B-tree

A binary search tree has 2 children per node, so its depth is about log2(N). If every node is a separate page, a lookup costs about one read per level.

A B-tree makes each node one page holding many keys, so each node has many children. This is the fan-out, written f. Depth becomes logf(N). A large fan-out makes the tree very shallow:

The same idea held in the lab: 200,000 reviews in store.reviews gave a collection tree of depth 3.

The three rules (the invariants)

A B-tree with minimum degree T keeps these rules after every operation:

  1. A page holds at most 2T − 1 keys. Every page except the root holds at least T − 1.
  2. Keys inside a page are sorted. A page with k keys has k + 1 children, and the keys separate the children's ranges.
  3. All leaves are at the same depth. The tree is always perfectly balanced.Comer 1979

How does it stay balanced? A full page splits: its middle key (the median) moves up into the parent. The tree only gets taller when the root splits. So it grows from the top, never from the bottom, and every leaf stays at the same depth.

Part 2 · Build one in C

The full file is lessons/code/btree.c (about 150 lines). It uses T = 2, so a page holds at most 3 keys. That's tiny on purpose, so splits happen often enough to watch. The keys are plain integers. Read them as RecordIds in the reviews collection table: that's exactly what a collection B-tree is keyed by.

cd ~/Development/foundaments/mongodb/lessons/code
cc -std=c11 -Wall -o btree btree.c && ./btree

The page

#define T 2
#define MAX_KEYS (2 * T - 1)

typedef struct Node {
    int n;                       /* number of keys currently stored        */
    int keys[MAX_KEYS];          /* sorted keys                            */
    struct Node *child[2 * T];   /* child[i] holds keys < keys[i]          */
    bool leaf;
} Node;

Search: one page per level

static bool btree_search(Node *x, int k) {
    pages_visited++;
    int i = 0;
    while (i < x->n && k > x->keys[i]) i++;          /* find first key >= k   */
    if (i < x->n && k == x->keys[i]) return true;    /* found on this page    */
    if (x->leaf) return false;                       /* nowhere left to go    */
    return btree_search(x->child[i], k);             /* descend one level     */
}

Split: the heart of the B-tree

static void split_child(Node *parent, int i) {
    Node *full = parent->child[i];
    Node *right = node_new(full->leaf);
    right->n = T - 1;
    for (int j = 0; j < T - 1; j++)                  /* upper half of keys    */
        right->keys[j] = full->keys[j + T];
    if (!full->leaf)
        for (int j = 0; j < T; j++)                  /* ...and their children */
            right->child[j] = full->child[j + T];
    full->n = T - 1;                                 /* left keeps lower half */
    /* ...shift parent's keys/children right to make room... */
    parent->child[i + 1] = right;
    parent->keys[i] = full->keys[T - 1];             /* median moves UP       */
    parent->n++;
}

Insertion walks down from the root and splits any full page before entering it. That guarantees there is always room for the median, so it never has to walk back up. If the root itself is full, a new empty root is created above it first. That is the only moment the tree gets taller. (This is the algorithm from CLRS, Introduction to Algorithms, chapter 18.)

Answers (only after predicting!)
  1. The page [10 20 30] is full and it's the root, so it splits. 20 moves up into a new root, and the height goes from 1 to 2. Result: [20] over [10] [30 40].
  2. A search can only say "not here" after reaching a leaf, so a miss walks the full height too. Both cost 3 pages, the tree's height. (In lesson 0002's lab, that's why a query for a non-existent key isn't free.)
  3. Height 2: [40 60] over three leaves. Bigger pages → more fan-out → shorter tree. That's the whole argument of Part 1, in miniature.
  4. Height 4, and almost every leaf holds just 1 key, the minimum. The split puts half the keys in each new page, and ascending inserts never return to the left half. So pages stay half-empty. Keep this in mind: insert order changes how full pages are.

Part 3 · WiredTiger's B-tree: four differences from the textbook

Our C tree is the textbook version. WiredTiger keeps the same shape: a root, internal pages, and leaves, all kept sorted, with pages that split when they reach a configured limit.WT B-trees Almost everything else is engineered for real storage and many threads.

1 · Data only in the leaves

Look at the C output: 40 is stored in the root, and the root is where you'd find it. WiredTiger doesn't do that. "The root and internal pages only store keys and references to other pages, while leaf pages store keys and values."WT B-trees Internal pages are pure signposts. When a page's first key is needed for routing, a copy of it goes up to the internal page, and those copies can be trimmed with prefix/suffix compression.WT row/column (This design is often called a B+-tree.)

Why it matters: every lookup ends at a leaf, so cost = tree depth, and a range scan reads only leaves. That's exactly the IXSCAN behaviour from lesson 0002.

2 · Every page has two forms, and a pointer isn't always a pointer

In C, child[i] is a memory address. The child is always there. In WiredTiger, a child reference is a WT_REF with a state:btmem.h

  • WT_REF_DISK: "the page is on disk, and must be read into memory before use"
  • WT_REF_MEM: the page has been read into memory
  • WT_REF_LOCKED: "locked for exclusive access"

A page on disk is a compact block: a page header, "immediately followed by the block header", and then cells (keys, values, off-page addresses). Each block may be compressed and/or encrypted, but "the header portion of each block remains uncompressed and unencrypted".WT data file Here is one, byte by byte:

How to read it:

  • Headers first, 40 bytes. The 28-byte page header (WT_PAGE_HEADER) says what the page is: its type, how many cells it has (entries), and how big it will be once built in memory (mem_size). The 12-byte block header belongs to the block manager: the block's size on disk and its checksum.btmem.hblock.h
  • The first 64 bytes are never compressed (WT_BLOCK_COMPRESS_SKIP), so WiredTiger can read the headers before it decompresses anything.block.h
  • Then cells, in key order. A row-store leaf is a key cell followed by a value cell, again and again.WT data file In a collection, the key is the RecordId and the value is the BSON document. In an index leaf, the keys are index keys, prefix-compressed: a shared prefix is "stored only once per page". A value can also carry a time window, its visibility timestamps (lesson 4).
  • Internal pages hold key + address pairs. The address cell is the on-disk "pointer": where the child block is in the file, how big it is, and its checksum. The checksum is stored twice, in the parent's address and in the child's own header. That helps catch corruption, and also bugs like a page overwritten by another valid page.block.h

When a thread needs that page, WiredTiger reads the block, decrypts and decompresses it, and builds in-memory structures for binary search.WT cache The in-memory layout is "optimized for fast, concurrent access by multiple application threads". The disk layout is optimized for space.WT cache

3 · Changes don't edit the page. They hang off it.

In our C code, inserting means shifting keys inside the array. With many threads reading the same page, that would be a disaster. So WiredTiger leaves the page's original contents alone:btmem.h

  • Existing keys sit in an array of WT_ROW, "sorted by key, fixed in size", pointing at the on-page data.
  • New keys go into skip lists of WT_INSERT items. Each node gets "a randomly chosen depth of next pointers". A skip list is a sorted linked list with express lanes, searchable in O(log N).WT glossary
  • New versions of a key are WT_UPDATE structures "formed into a forward-linked list", the update chain. Keeping several versions is what makes snapshots (MVCC) possible. That's lesson 4.

Readers use hazard pointers, "a data structure that assists in lock free algorithms, used by WiredTiger Btrees".WT glossary A thread announces "I'm using this page" without taking a lock, and eviction must not remove a page while such a pointer is held. WiredTiger's own bug tracker records cases where hazard pointers blocked eviction.WT-486

4 · It never overwrites a block on disk

To write a changed page, WiredTiger first reconciles it: it converts the in-memory page, with its skip lists and update chains, back into a compact disk image.WT cache Then the block manager writes that image to a new location. It is a no-overwrite system: "once a block is written it cannot be modified."WT block manager

This is why the lesson-1 diagnostic said the previous checkpoint "stays valid" during a crash. Its blocks were never touched. A block can even belong to several checkpoints.WT block manager

So, in production…

  • Deleting data doesn't shrink .wt files. Freed blocks go onto the avail list for reuse. The file only shrinks when free space sits at the very end, which is what compaction works toward.WT block manager Expect disk usage to stay flat after a big delete.
  • Pages are the unit of everything: I/O, cache, compression and splitting. Collection leaf pages max out at 32 KB in your lab, and index pages at 16 KB.
  • Very large values don't fit on a page and become overflow pages, stored separately.WT glossary
  • A very hot page touched by many threads can be hard to evict, because of hazard pointers. WiredTiger engineers track this as a latency source.WT-12860
