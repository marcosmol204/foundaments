Concurrency: snapshots and write conflicts

Many clients read and write the same reviews at once. Nobody waits for a lock on the collection, and no vote is lost. This lesson is about how, and about the bill that comes later.

Your win today: look at a writeConflicts counter that's climbing, or a cache that fills up while one transaction sits idle, and name the mechanism behind it and the metric that proves it.

0 · Warm-up from lesson 3

From memory, before reading on: when eviction writes a dirty page, the latest values go to the data file. Where do the older versions go, and who still needs them? Lesson 3 left the "who" open. This lesson answers it.

One new field. Our examples need a number that many clients change at once, so I'm adding helpful: number to store.reviews: the "was this review helpful?" vote counter. The five standard fields stay as they are. The lab adds it with $inc.

1 · Two layers, two kinds of concurrency control

Lesson 2 split mongod into the MongoDB layer and WiredTiger. Each one controls concurrency in its own way:concurrency FAQ

LayerWhat it protectsHow
MongoDBglobal, database, collectionLocks. For normal reads and writes, only intent locks.
WiredTigereach document (each key in a table)No locks. Snapshots for reads, conflict detection for writes. This is optimistic concurrency control.

An intent lock says "I'm going to work on something inside this". Reads take IS (intent shared) and writes take IX (intent exclusive) on the global, database and collection levels. IX is compatible with IX, so any number of writers can be inside store.reviews at once. "For most read and write operations, WiredTiger uses optimistic concurrency control. WiredTiger uses only intent locks at the global, database and collection levels."docs Full S and X locks are for rare operations. For example, renameCollection can need an exclusive database lock.docs

In serverStatus().locks and currentOp, the modes are written as letters: r = IS, w = IX, R = S, W = X.concurrency FAQ In the lab, an idle transaction and a blocked update on the same review both held Collection: "w" at the same time. So the collection lock was not what blocked anything. The rest of the lesson is what did.

2 · A snapshot is three numbers

WiredTiger uses MVCC (multi-version concurrency control): "At the start of an operation, WiredTiger provides a point-in-time snapshot of the data to the operation."docs A snapshot is not a copy of the data. It is a small record of which transactions count as done:WT snapshot

  • Every write transaction gets a transaction ID from a global counter that only goes up.
  • A snapshot stores the max ID seen when it was taken, the list of concurrent transactions (still running at that moment), and the min ID.

To decide whether a change made by transaction t is visible, WiredTiger checks in this order:WT snapshot

  1. t ≥ max → invisible (it started after the snapshot).
  2. t < min → visible (it finished before the snapshot).
  3. t is in the concurrent list → invisible (it wasn't committed yet).
  4. Otherwise → visible.

That's the whole rule. Readers never wait for writers, and writers never wait for readers: a reader just skips the versions it isn't allowed to see.

3 · One review's update chain, step by step

Where do the versions live? Lesson 2.1 showed that each in-memory leaf page keeps changes in update lists. "The in-memory updates in WiredTiger are organized as a singly linked list with the newest update at the head."WT transactions Each update carries the ID of the transaction that wrote it (the WT_UPDATE struct in btmem.h). We follow one review, R, the first one in the seed data: {_id: ObjectId('6955b900…'), rating: 4, verified: true, helpful: 1}.

Walkthrough 1 · A reader takes a snapshot

  1. R's helpful: 1 was written long ago. It's in the on-disk image of the page.
  2. Transaction 104 (someone's vote) runs $inc: {helpful: 1}. It hasn't committed yet. R's chain is now [104: helpful 2] → disk value helpful 1.
  3. A moderation dashboard starts reading. Its snapshot S is {min 104, max 106, concurrent [104]}.
  4. 104 commits. S doesn't care: 104 is in its concurrent list, so S still skips it and reads helpful: 1. S sees the same R for its whole life, which is what snapshot isolation means.WT transactions

Walkthrough 2 · A second voter, a second reader

  1. Transaction 107 votes too: helpful 3, not committed yet. It goes at the head of the chain.
  2. A new reader T starts: {min 107, max 108, concurrent [107]}. It skips 107 (concurrent) and reaches 104. 104 < min, so it's visible: T reads helpful: 2.
  3. S reads R again. 107 ≥ its max, 104 is concurrent: still helpful: 1. If no version on the chain is visible, the reader falls back to the on-disk value.WT transactions

Walkthrough 3 · A third voter hits a write conflict

  1. Transaction 108 wants to $inc R as well. Before it adds an update, WiredTiger looks at the head of the chain: 107, which is not visible to 108, because it isn't committed.
  2. If 108 wrote helpful 3 on top, 107's vote would be lost. So WiredTiger refuses: it returns WT_ROLLBACK with the reason "conflict between concurrent operations" (newer WiredTiger versions prefix it with "Write") and counts it in the update conflicts stat.txn_inline.h
  3. The same happens if the head is committed but committed after 108's snapshot was taken. The rule is "the newest version must be visible to me". So the first writer wins, and the second one has to start over.

Timestamps, briefly

MongoDB adds a second clock on top of transaction IDs. Writes are labelled with a commit timestamp, and a snapshot can be opened at a timestamp. It then sees "all data committed with a timestamp less than or equal to the snapshot's timestamp".storage README (Where MongoDB gets those timestamps is part of lesson 6.) WiredTiger says the same thing from below: "A transaction can only see updates with timestamps smaller or equal to its read timestamp."WT transactions Two global timestamps matter:

  • Oldest timestamp: "the timestamp that should be visible by all concurrent transactions". Nobody may read before it, so versions older than it can be thrown away.WT transactions MongoDB moves it forward, but keeps at least minSnapshotHistoryWindowInSeconds of history, 300 s by default, so that snapshot reads at a past cluster time still work.params
  • Stable timestamp: used by checkpoints and recovery. That's durability, lesson 5.

4 · From WT_ROLLBACK to your app

WiredTiger only says "roll back". MongoDB decides what to do with it. The storage layer turns WT_ROLLBACK into a WriteConflictException.wiredtiger_util.cpp Then it depends on whether you're in a multi-document transaction:

Your operationWhat happens on a write conflict
Plain write: updateOne, insertOne…Retried inside the server by writeConflictRetry, with backoff, with no upper limit. Each retry adds 1 to writeConflicts. Your app just sees success, a bit later.exception_util.h
Inside a transactionNot retried. The transaction aborts and you get WriteConflict with the label TransientTransactionError. Your code (or the driver's withTransaction) must retry the whole transaction.storage README

The storage README calls this design "optimistic concurrency control because it allows un-contended writes to commit quickly".storage README No lock is taken in the normal case. The cost only shows up when two writers really touch the same document.

One case looks like waiting, but isn't. "If a transaction is in progress and has taken a lock to modify a document, when a write outside the transaction tries to modify the same document, the write waits until the transaction ends."txn docs Under the hood, the plain write keeps hitting the uncommitted head of the chain and keeps retrying. In the lab, a write stuck behind an open transaction for 2 s retried 204 times, and currentOp showed waitingForLock: false.

5 · The bill: long snapshots pin history

When can WiredTiger throw away [104: helpful 2]? Only when no snapshot could ever need it again. That means every running snapshot, and the oldest timestamp, must be past it. The oldest snapshot still open sets the limit for the whole server, for every collection, not just the documents it read.WT history store

  1. Your reporting job opens a transaction, reads one review, then waits on something slow.
  2. Meanwhile, normal traffic writes 300,000 votes. Each one adds a version to some update chain. None of the old versions can be dropped, because the report might still read them.
  3. The chains grow, and the pages holding them are dirty. That's lesson 3's dirty share going up.
  4. When those pages are reconciled, the old versions are moved to the history store, WiredTigerHS.wt: "All older updates are added to the history store table assuming they are not yet obsolete."WT history store That's more writes, and the history store is one more table in the cache.
  5. The report ends. Everything it pinned becomes obsolete at once and can be cleaned up.

MongoDB puts two limits on this. A transaction older than transactionLifetimeLimitSeconds (60 s by default) is aborted by a periodic cleanup, which "helps relieve storage cache pressure".params And when the cache is under pressure, the transaction holding the oldest snapshot can be rolled back for eviction. You'll see a WriteConflict (or TransactionTooLargeForCache) for a transaction that never touched a contended document.txn docs

Lab result (100,000 reviews, history window set to 0 to isolate the effect, 3 passes of $inc: {helpful: 1} over every review):

Runtransaction range of IDs currently pinnedhistory store table insert calls (Δ)
No open snapshot (2 runs)0 and 5,55849,363 and 14,353
One idle snapshot transaction (2 runs)300,018 both times273,108 and 291,321
Default 300 s window, no open snapshot0253,467

The idle transaction pinned exactly the 300,000 updates that ran after it, plus a few internal ones, and it pushed 6–20× more versions into the history store. The last row is a surprise worth remembering: on a replica set, the default 300 s window pins history even with no open transaction. Five seconds after the transaction was aborted, the pinned range was back to 0.

6 · So in production you should…

Rule: keep transactions short, and keep hot single documents rare. A long snapshot makes the whole server keep history. A document that every request updates turns parallel writers into a retry loop.

  1. Avoid hot-spot documents. Two clients voting on the same review conflicted about once every 6 updates in the lab. Two clients voting on different reviews conflicted 0 times. If one document takes all the writes (a global counter, a "stats" document), spread the writes out, for example one counter document per bucket, added up at read time.
  2. Keep transactions short, and never wait on users or network calls inside one. Read what you need, write, commit. Always abort transactions you abandon.txn docs
  3. Retry whole transactions on TransientTransactionError. Use the driver's withTransaction callback API, which does it for you. Single writes don't need this: the server already retries them.
  4. Don't raise minSnapshotHistoryWindowInSeconds or transactionLifetimeLimitSeconds without a reason. Both make WiredTiger keep more history. The manual warns that a bigger window "increases disk usage".docs

    The newest version of R (B's update) was committed after A's snapshot, so it isn't visible to A. A can't write on top of it.
  5. A plain write behind an open transaction. 
    // A: change R in a transaction and leave it open

// B: this will hang

// A: watch B retry (the db variable is outside the session)

db.getSiblingDB('admin').aggregate([{ $currentOp: {} }, { $match: { ns: 'store.reviews', op: 'update' } },
