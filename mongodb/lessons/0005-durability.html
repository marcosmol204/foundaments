Durability: journal and checkpoints

Your write is acknowledged while it still lives in memory. This lesson is about the two mechanisms that make sure it survives a crash anyway, and what they cost you in latency.

Your win today: say exactly when a review you inserted becomes crash-safe (with and without j: true), read the recovery lines in a mongod log after a kill -9, and use two serverStatus() numbers to tell "slow fsync" from "slow checkpoint".

0 · Warm-up

From memory, before reading on:

  1. Lesson 2.1: when WiredTiger writes a changed page to disk, does it overwrite the old block? What does the old block stay useful for?
  2. Lesson 3: name the two things that write dirty pages out of the cache.

You asked earlier where the journal fits next to a collection's B-tree (it's in your questions). The short answer was "a separate append-only log, replayed after a crash". Today we make that precise, and there's a twist in section 5: in a replica set, the journal doesn't hold your reviews at all.

1 · Why two mechanisms?

Put lessons 2.1 and 3 together and you get a problem.

  • The cache keeps changes in memory. An insert into store.reviews changes a leaf page in the WiredTiger cache and marks it dirty (lesson 3). The .wt file doesn't have it yet.
  • Writing the page at every commit would be expensive. A review is ~165 bytes, but the leaf page is up to 32 KB. And WiredTiger never overwrites a block: the new page image goes to a new block.WT block manager So the parent's address for that leaf changes, so the parent must be rewritten too, and so on up to the root. One small insert would become several random page writes.

So WiredTiger splits the job in two:docs

Journal (write-ahead log)Checkpoint
What is writtenA small log record per commit: "insert this review"Every dirty page, up to a new root, for every table
HowAppended to the end of one file: sequential, cheapNew blocks scattered in many .wt files
How oftenSynced every 100 ms, or right away for j: truejournalingEvery 60 sdocs
Its jobMake each commit durable quicklyMake a consistent copy of the data files, so the journal can be thrown away

Neither one is enough alone. Without the journal you'd lose up to 60 s of writes on a crash. Without checkpoints the journal would grow forever, and a restart would have to replay all of it.

2 · One review, step by step

We follow one review, R, on a standalone mongod (the replica set version comes in section 5):

db.reviews.insertOne({ review: "After two weeks battery lasts for days.", rating: 5,
                       tags: ["battery", "quality"], verified: true })

Walkthrough 1 · Commit

  1. WiredTiger adds R to leaf page P in the cache. P is now dirty (lesson 3).
  2. In the same commit, it builds a log record for R and copies it into an in-memory log buffer.WT logging Nothing is on disk yet.
  3. With the default write concern (w: 1, no j), the server acknowledges now. Your app thinks R is saved, but if mongod dies in the next few milliseconds, R can be lost: "updates can be lost following a hard shutdown".journaling

Walkthrough 2 · The journal sync (≤ 100 ms later)

  1. A background thread, the JournalFlusher, wakes up every commitIntervalMs (default 100).journal_flusher.hstorage_options.h
  2. It asks WiredTiger to write the log buffer to the journal file and fsync it. Now R survives a crash, even though P is still only in memory.
  3. With j: true, the server doesn't wait for the timer. It requests a flush right away and acknowledges only after the sync.journaling

Walkthrough 3 · Eviction may write P (or not)

  1. If P gets evicted, it's reconciled and written to a new block (lesson 3). But that block isn't part of any checkpoint yet. If the server crashed now, recovery would ignore it and rebuild R from the journal.

Walkthrough 4 · The checkpoint (≤ 60 s later)

  1. The checkpoint writes every dirty page, including P, plus the parents up to a new root (section 4).
  2. When it finishes, R is in the data files. The journal records before this checkpoint aren't needed any more, and old journal files are deleted.WT logging

Walkthrough 5 · A crash between the two

  1. Restart opens the data files as of the last checkpoint (C1). R isn't there.
  2. WiredTiger replays the journal from C1 to the end. R's record is in it, so R comes back.journaling Section 6 shows this in a real log.

3 · The journal up close

  • Log records. "The unit written to the write-ahead log is a log record." Each record has a 16-byte header and is padded to a multiple of 128 bytes.WT logging A record's position is its LSN (log sequence number): a file number plus a byte offset, like 2/34762624. You'll see LSNs in the recovery log.
  • Files. The journal is <dbPath>/journal/WiredTigerLog.<sequence>, ~100 MB each.journaling WiredTiger creates the next file ahead of time (WiredTigerPreplog.* in the lab), so a full file doesn't stall writers.WT logging
  • Compression. Snappy by default (journalCompressor). Records of 128 bytes or less aren't compressed.docs
  • Always on. Since 6.1 you can't turn the journal off.journaling

Group commit: why j:true isn't as bad as it sounds

An fsync waits for the disk. If 100 clients each needed their own fsync, they'd queue. Two layers prevent that:

  1. WiredTiger slots. "WiredTiger has a pool of log buffers called slots." Concurrent commits join the same slot without locks, so one write to the file carries many records.WT logging
  2. MongoDB's flusher. "Asynchronously grouping data flush requests reduces the total number of flushes executed."journal_flusher.h A j: true waiter that arrives while a sync is running just waits for the next one. In the code: "Someone else synced already since we read lastSyncTime, so we're done!"session_cache.cpp

The same idea works inside one client: an insertMany of 2,000 reviews with j: true costs one sync, not 2,000.

What I measured

mongo:8.0 (8.0.34) in Docker on a laptop SSD, 200,000 seeded reviews, 2,000 insertOnes per run from mongosh inside the container (lab step 3):

Write concernp50p99Journal syncs during the run
{w: 1} (j false), standalone0.16–0.18 ms0.24–0.59 ms3–4 (the 100 ms timer)
{w: 1, j: true}, standalone0.25–0.27 ms0.80–0.92 ms2,001–2,002 (one per insert)

The average sync took about 0.14 ms (log sync time duration ÷ log sync operations). That's very fast: Docker's VM disk on a laptop SSD. On a real server, especially with network-attached cloud disks, each sync can cost much more, and j: true latency is roughly your fsync time. Measure yours with the same two stats (section 7).

4 · Checkpoints up close

"A checkpoint is a known point in time from which WiredTiger can recover in the event of a crash or unexpected shutdown."WT checkpoint Here is what one does, in order:

  1. Eviction first. Before it starts, "the eviction subsystem is leveraged to reduce the dirty content in the cache", so there's less left for the checkpoint itself.WT checkpoint
  2. Take a snapshot. "A checkpoint is performed within the context of a snapshot isolation transaction", so "the checkpoint has a consistent view of the database from beginning to end." Writes keep going meanwhile. They're just not part of this checkpoint. (Snapshots are lesson 4.)
  3. Walk every B-tree. "All the dirty pages are reconciled." "Clean pages are skipped."WT checkpoint Each written page goes to a new block, so its parent changes, up to a new root per tree. The history store (WiredTigerHS.wt, lesson 4) is checkpointed too.
  4. Metadata last. Each tree's new root address goes into its entry in WiredTiger.wt, the metadata table. "The metadata file is the last file to be checkpointed." Then the turtle file is updated to point at that new metadata checkpoint.WT metadataWT checkpoint

The manual says it plainly: "During the write of a new checkpoint, the previous checkpoint is still valid." The new one "becomes accessible and permanent when WiredTiger's metadata table is atomically updated to reference the new checkpoint."docs After that, blocks only the old checkpoint used (here @A, @B, @D) are freed for reuse.

Who starts it, and when

A MongoDB thread, the Checkpointer, sleeps syncdelay seconds (default 60, config name storage.syncPeriodSecs), then asks WiredTiger for a checkpoint.checkpointer.cppstorage_options.h The wait starts after the previous one finishes, so a checkpoint that takes 40 s is followed by the next one 60 s later, not 20.

What I measured

In the lab, the first checkpoint came at ~60 s of uptime. Every checkpoint took 12–14 ms (most recent time (msecs)). I then tagged all ~214,000 reviews with $addToSet: {tags: "moderated"}: dirty data jumped to 9.1%, but eviction workers brought it down to ~3% within a second (lesson 3's 5% dirty target). The next checkpoint still took 12 ms, and a steady stream of ~6,000 inserts/s showed no latency change around it (p99 0.2–0.5 ms most seconds; the few outliers didn't line up with the checkpoint). On a small cache and a fast SSD, there's little to write. Section 7 explains when that changes.

5 · The stable timestamp (and the twist)

Everything above is a standalone server. A replica set adds one rule. Keep this light for now: lesson 6 does replication properly.

  • In lesson 4 you saw that each update in an update chain carries a timestamp. The replication layer tells WiredTiger a stable timestamp: roughly, the newest point that a majority of members have, so it can never be rolled back.repl README "The stable timestamp defines the point that divides the stable part of the time window from the unstable part."WT timestamps
  • MongoDB takes stable checkpoints: WiredTiger sets "the checkpoint_timestamp to be the current stable_timestamp".WT checkpointkv_engine.cpp Updates newer than that stay out of the checkpoint, even if they're committed. Why: a write a majority doesn't have yet might be rolled back after a failover. The data files should never contain something that might have to be undone.

The twist. In a replica set, store.reviews is created with log=(enabled=false): its changes are not journaled. Only the local database is, which includes the oplog.wiredtiger_util.cpp Every write to reviews also writes an oplog entry in the same transaction, so the journaled oplog is the write-ahead log for your reviews. "The user writes themselves, however, on a --replSet server, do not need to be written out to disk."storage README

StandaloneReplica set member
Journaled tablesAlllocal.* (oplog), not store.reviews
CheckpointEverything committedUp to the stable timestamp
After a crashLast checkpoint + WiredTiger journal replayStable checkpoint + journal (oplog is back) + oplog replay from the stable timestamp

I checked the first row in the lab: on a one-node replica set, db.reviews.stats().wiredTiger.creationString contains log=(enabled=false), and the oplog's contains log=(enabled=true).

6 · Crash recovery

The manual's three steps: find the last checkpoint in the data files, find its position in the journal, and "apply the operations in the journal files since the last checkpoint".journaling WiredTiger finds the last checkpoint through the turtle file: "Using the turtle file, WiredTiger can read the latest checkpoint information."WT metadata After replay, it runs rollback to stable, which removes anything newer than the stable timestamp from non-logged tables, then takes a fresh checkpoint.WT RTS

Here's what the log said in the lab, on a standalone. I inserted 50,000 reviews with {w: 1}, one marker review with j: true, then one more with j: false, and ran docker kill --signal=KILL right away (lab step 5; lines trimmed):

Detected unclean shutdown - Lock file is not empty
Recovering data from the last clean checkpoint.
Main recovery loop: starting at 2/34762624 to 3/256
recovery log replay has successfully finished and ran for 404 milliseconds
Set global recovery timestamp: (0, 0)
recovery rollback to stable has successfully finished and ran for 0 milliseconds
recovery checkpoint has successfully finished and ran for 14 milliseconds
recovery was completed successfully and took 418ms, including 404ms for the log replay, ...
  • 2/34762624 is the checkpoint's LSN: file WiredTigerLog.0000000002, byte 34,762,624. Replay ran from there to the end of the journal, about 40 MB, in 404 ms.
  • Recovery timestamp (0, 0): a standalone has no stable timestamp, so its checkpoints aren't timestamped.
  • All 50,002 reviews were there after restart, both markers included. The j: false one survived because the kill came ~180 ms later, after a timer sync. That's luck, not a guarantee.

The same crash on a one-node replica set added the replication part after WiredTiger's own recovery:

Set global recovery timestamp: (1793099803, 1)
recovery was completed successfully and took 176ms, including 156ms for the log replay, ...
Recovering from stable timestamp  {stableTimestamp: (1793099803, 1), topOfOplog: (1793099821, 815)}
Replaying stored operations from startPoint (exclusive) to endPoint (inclusive)
Completed oplog application for recovery  {numOpsApplied: 4517, numBatches: 66}

The stable checkpoint was 18 seconds behind the top of the oplog, so the server re-applied 18 s of oplog (4,517 entries) to bring store.reviews up to date. The repl README describes this as "startup recovery".repl README

7 · So in production you should…

Rule: j: true latency is your fsync latency, and checkpoint cost is your dirty data. Watch both, and put the data on a disk that syncs fast.

The stats

All in db.serverStatus().wiredTiger. Take two snapshots and use the difference, as in lesson 3. Names checked on 8.0.34.

StatWhat it tells you
log["log sync time duration (usecs)"] ÷ log["log sync operations"]Average fsync time. Roughly what each j: true write waits.
log["log bytes written"]Journal write volume. With a long checkpoint, this tells you how much replay a crash would cost.
checkpoint["most recent time (msecs)"], checkpoint["max time (msecs)"]How long checkpoints take. Approaching 60 000 means checkpoints run back to back.
checkpoint["total succeed number of checkpoints"]Should go up about once a minute. If it stalls, the journal can't be trimmed.
cache["tracked dirty bytes in the cache"] (lesson 3)How much the next checkpoint will have to write.

  1. Know what j: false means. With {w: 1}, an acknowledged review can disappear on a hard crash, up to ~100 ms of them. If a lost review is unacceptable, use j: true, or in a replica set w: "majority", which implies j: true by default (writeConcernMajorityJournalDefault).journaling Lesson 6 covers why majority is the real answer.
  2. Batch durable writes. One insertMany of 2,000 reviews with j: true cost one sync in the lab. 2,000 separate insertOnes cost 2,000.
  3. Size checkpoints by the dirty cache, not by write rate. Eviction workers keep dirty data near 5% of the cache (lesson 3). With a 30 GB cache, that's ~1.5 GB a checkpoint may have to write in one burst. A disk that writes 100 MB/s needs 15 s for it, and your reads and journal syncs share that disk the whole time. The lab's 12 ms checkpoints wrote a few MB to an SSD.
  4. Leave syncPeriodSecs and commitIntervalMs alone. The source comment on syncdelay: "In almost every situation you should not set this value and use the default setting."storage_parameters.idl Fix the disk instead.
  5. Keep free disk space for the journal. Files are preallocated in 100 MB steps, and "If you do not set aside enough disk space for your journal files, the MongoDB server will crash."journaling
