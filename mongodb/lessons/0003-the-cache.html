The cache

Pages live on disk. Queries only work on pages in memory. This lesson is about what moves them back and forth, and who pays when it's slow.

Your win today: look at a latency problem and three numbers from serverStatus(), then say whether your working set fits in the cache, and whether your own queries are being forced to do eviction work.

0 · Warm-up from lesson 2

From memory, before reading on: a WiredTiger B-tree has a root page, internal pages and leaf pages. Which ones hold the documents? Which ones does every single seek pass through? Keep your answer in mind. Section 2 depends on it, and the quiz will ask again.

1 · Two memories, two formats

A page can be in three places. MongoDB uses two memory caches, not one.docs

  • WiredTiger cache. "Memory used to hold copies of recently accessed or modified data."WT cache Pages here use a different layout from disk, built for fast access by many threads. Collection data is uncompressed here. Indexes keep their prefix compression.docs
  • Filesystem cache. The OS keeps recently read file blocks in free RAM, in the same compressed format as on disk.docs If WiredTiger misses but the OS cache hits, the read costs a decompression, not a disk I/O.

That's why the 7.5 GB number from the diagnostic mattered. The default WiredTiger cache is the larger of 50% × (RAM − 1 GB) or 0.256 GB.docs On a 16 GB server that's 7.5 GB. The other half isn't wasted: it's the OS cache, which holds compressed data, so it fits more of your data per GB.

In the lab (2,000,000 reviews, ~164 bytes each), store.reviews was 314 MB uncompressed but only 80 MB on disk. So the same reviews take about four times as much room in the WiredTiger cache as in the OS cache. (The seed script reuses a few phrases, so its text compresses better than real reviews would. The direction is the same, though.)

2 · One page's life, step by step

We follow a single leaf page of store.reviews. Call it P. Reviews are stored in RecordId order, which here is creation order, so P holds about 200 reviews written between 00:00 and 00:03 on 10 January 2026. The tree has depth 3, like the lab collection in lesson 2.

Walkthrough 1 · First read (a miss)

  1. Your app asks for the reviews of 10 January, so it needs the reviews on P. The seek starts at the root. The root and the internal page are already in cache, because every seek passes through them.
  2. The internal page points to P, but P is not in cache. That's a miss. "Lookups start at the root and load any missing page from storage as they descend."WT cache
  3. WiredTiger asks the block manager for P's block. The OS serves it from its cache or from disk.
  4. WiredTiger decompresses the block and builds the in-memory page, with an index for binary search inside it.WT cache Then the query reads its documents.

Walkthrough 2 · Second read (a hit)

  1. The same query runs again. Root → internal → P, and all three are in memory.
  2. No I/O and no decompression. In the lab, this made the same query about 1.6× faster (33–37 ms vs. 53–65 ms cold; numbers in section 5).

Walkthrough 3 · A write makes P dirty

  1. A moderator edits one review on P, say $addToSet: {tags: "moderated"}. WiredTiger does not rewrite P on disk. It adds the change to P's in-memory update list (lesson 2).
  2. P is now dirty: the in-memory copy is newer than the disk copy. The cache tracks clean bytes and dirty bytes separately.WT cache
  3. Is the change lost if the server crashes now? No. The journal has it (lesson 5). The .wt file just doesn't have it yet.

Walkthrough 4 · P gets evicted

  1. Other pages keep arriving. P isn't used for a while, so it becomes one of the least recently used. Eviction sorts candidates by last access and takes the oldest third, "an approximate Least Recently Used (LRU) algorithm".WT eviction
  2. If P is clean: "WiredTiger simply frees the page's memory."WT cache That's cheap, because the disk copy is already correct.
  3. If P is dirty: WiredTiger must first reconcile it. Reconciliation turns it back into the on-disk format and writes it out. The latest values go to the data file, and older versions still needed by readers go to the history store (WiredTigerHS.wt, lesson 4).WT eviction Only then is the memory freed. That's much more expensive.
  4. The next query that needs P starts over at Walkthrough 1.

Eviction isn't the only thing that writes dirty pages. Checkpoints write them too, every 60 seconds,docs but the pages stay in cache afterwards, now clean.WT cache

3 · Who does the evicting?

Eviction normally runs in background eviction worker threads. MongoDB 8.0 starts exactly 4 of them (eviction=(threads_min=4,threads_max=4)).kv_engine.cpp When they can't keep up, the threads running your queries get pulled in: they "are also forced to do the work of eviction workers threads … before they can read or write more data."WT eviction

Four thresholds decide this. They are percentages of the cache size, and MongoDB keeps WiredTiger's defaults:WT config

Two consequences:

  • A cache that's ~80% full is normal. The workers hold it there on purpose. In the lab, right after loading, the cache sat at 203.9 of 256 MB, which is 79.6%. "Cache 80% full" alone is not an alert.
  • The latency cliff is at the triggers. Past 95% full, or 20% dirty, your request does housekeeping before it can do its own work. That's the p99 spike from diagnostic Q16.

4 · Try it: a 20-page cache

A small model with the same rules: LRU eviction, 80/95 total thresholds, 5/20 dirty thresholds. Clean evictions cost workers 1 unit and dirty ones cost 2. Read a few pages by hand first, then play the scenarios. Predict before you press play: what is the hit rate on the second pass of the scan?

Things to try:

  1. Hot set fits: 10 misses to warm up, then every read is a hit.
  2. Scan bigger than cache ×2: 60 pages through a 20-page cache. With LRU, the second pass gets zero hits: each page was evicted just before it was needed again.
  3. Switch to workers too slow and run the scan again. The cache hits the trigger, and "by your thread" starts counting.
  4. Write burst: dirty pages cost workers twice as much, so writers reach the dirty trigger even with fast workers.

This is a teaching model. Real WiredTiger samples pages instead of keeping a perfect LRU list, and its pages vary in size.

5 · What the real engine did

I ran all of this on mongo:8.0 (8.0.34) with the cache limited to 256 MB. store.reviews had 2,000,000 reviews: 314 MB of data, 80 MB on disk. The test query was "all reviews from 10 January", which is 86,400 reviews, read as an _id range (one review per second). You can repeat it in the lab below.

ExperimentPages read into cacheResult
One day of reviews, cold (restart + OS cache dropped)25353–65 ms
Same, OS cache warm (restart only)25341–47 ms (one run 78)
Same, WiredTiger cache warm033–37 ms
Full collection scan #13,0201,518 pages evicted
Full collection scan #2, nothing changed2,5672,252 pages evicted
Backfill: verify every unverified review, one day per batchn/adirty peaked at 19.6%, dirty trigger reached 5 times, 2,866 dirty pages reconciled

Times are executionTimeMillis for 4 runs each, on a laptop SSD. On networked cloud disks, each miss usually costs more, so the cold/warm gap gets bigger. Three things to notice:

  1. A WiredTiger hit beats everything. On this fast SSD, a miss served by the OS cache wasn't reliably faster than a real disk read: the run-to-run noise was bigger than the gap. The clear win was having the pages already in the WiredTiger cache, with no I/O and no decompression.
  2. A scan bigger than the cache doesn't get faster the second time. 314 MB of uncompressed reviews can't fit in 256 MB. Scan #2 had to read ~2,500 pages again, like the simulator.
  3. The backfill walked right up to the cliff. Dirty data peaked at 19.6%, the "dirty trigger was reached" counter went up 5 times, and application threads were asked to evict 10 times. That's the edge from section 3. A slightly faster backfill, or one running next to normal traffic, would push your queries into eviction work.

6 · So in production you should…

Rule: keep your working set in the WiredTiger cache, and watch the read-in rate and application-thread eviction, not the fill percentage. The working set is the index pages and document pages your normal traffic touches.

  1. Read the right stats. In db.serverStatus().wiredTiger.cache, compare two snapshots and take the difference:
    StatWhat it tells you
    pages read into cacheMisses. In steady traffic, a high and constant rate means the working set doesn't fit.
    page evict attempts by application threads, application thread time evicting (usecs)Your queries doing eviction. This is the latency tax.
    tracked dirty bytes in the cache ÷ maximum bytes configuredDirty share. Getting close to 20% means writers are about to be throttled.
  2. Shrink the working set before you buy RAM. Covered queries (lesson 2) only touch index pages, which stay prefix-compressed in cache.docs Dropping unused indexes frees cache too, because every index is another tree competing for it.
  3. Don't raise the cache above the default. The manual says to avoid it.docs The rest of RAM is the OS cache. It holds compressed data, so it fits more of your reviews per GB.
  4. In containers, or with several mongods per host, set the size yourself. In my lab, 8.0 read the 2 GB container limit correctly and picked 512 MB (= 0.5 × (2 − 1)). But the manual warns that WiredTiger "may not account for the memory limits" in some cases. Set --wiredTigerCacheSizeGB, then check maximum bytes configured and hostInfo().system.memLimitMB.docs
  5. Large scans and backfills push your hot pages out. A one-off report that scans a big collection evicts the pages your normal traffic needs, and normal queries become misses afterwards. Run them off-peak, in batches, or on a dedicated secondary (replication phase). Bulk writes in throttled batches keep dirty data under 20%.

About 15 minutes. These are the same steps I ran. Your timings will differ, but the page counts should be close.

  1. Start a server with a small cache, so you don't need gigabytes of data: 
    docker run -d --name mongo-lab3 -m 2g mongo:8.0 --wiredTigerCacheSizeGB 0.25
docker cp lessons/code/seed-reviews.js mongo-lab3:/seed-reviews.js
docker exec mongo-lab3 mongosh store --eval 'const N = 2000000' --file /seed-reviews.js   # ~50 s
docker exec -it mongo-lab3 mongosh store
  2. Define a helper that prints cache-stat differences, and one that turns a January day into an _id (one review per second since 1 Jan 2026): 
    const C = () => db.serverStatus().wiredTiger.cache
function measure(f) {
  const a = C(); f(); const b = C()
  return { pagesRead: b["pages read into cache"] - a["pages read into cache"],
           appEvict: b["page evict attempts by application threads"] - a["page evict attempts by application threads"],
           cacheMB: Math.round(b["bytes currently in the cache"] / 2**20),
           dirtyPct: +(100 * b["tracked dirty bytes in the cache"] / b["maximum bytes configured"]).toFixed(1) }
}
const day = d => ObjectId.createFromTime(Date.UTC(2026, 0, d) / 1000)
const st = db.reviews.stats(); [st.size / 2**20, st.storageSize / 2**20]   // uncompressed vs on disk
  3. Restart to empty the WiredTiger cache, then read the reviews of 10 January twice. Predict pagesRead for each run first. 
    docker restart mongo-lab3 && docker exec -it mongo-lab3 mongosh store
    // paste the C, measure and day definitions again, then:
const jan10 = () => db.reviews.find({ _id: { $gte: day(10), $lt: day(11) } }).itcount()
measure(jan10)
measure(jan10)
    { pagesRead: 253, appEvict: 0, cacheMB: 19, dirtyPct: 0 }
{ pagesRead: 0, appEvict: 0, cacheMB: 19, dirtyPct: 0 }
  4. Scan the whole collection twice. No review has this exact text and review has no index, so it's a COLLSCAN: 
    const scan = () => db.reviews.find({ review: "nobody wrote this" }).itcount()
measure(scan)
measure(scan)
    { pagesRead: 2875, appEvict: 1, cacheMB: 194, dirtyPct: 0 }
{ pagesRead: 2500, appEvict: 5, cacheMB: 224, dirtyPct: 0 }
  5. Make pages dirty with a moderation backfill: tag two days of reviews as "moderated". Then watch the dirty share go down as eviction and the checkpoint write them out: 
    measure(() => db.reviews.updateMany({ _id: { $gte: day(5), $lt: day(7) } }, { $addToSet: { tags: "moderated" } }))
measure(() => {})   // run again a few seconds later
    { pagesRead: 3838, appEvict: 15, cacheMB: 171, dirtyPct: 10.8 }
{ pagesRead: 0, appEvict: 0, cacheMB: 160, dirtyPct: 3.6 }   // 5 s later: workers wrote most of it out
  6. Optional: see which tree uses the cache. db.reviews.stats({indexDetails: true}) has a wiredTiger.cache section for the collection and one per index. Mine showed 111 MB for the collection and 54 MB for _id_. The _id index is big here because every "reviews of a day" query goes through it.
