Elections, the commit point and rollback

What happens when the primary disappears: who becomes primary and when, which writes survive, and why a review you saw acknowledged can still vanish.

Your win today: you cut a primary off from its replica set, predict how long writes fail, which of its writes are lost, and where the lost documents end up. Then you pick write and read concerns for store.reviews to match what you can afford to lose.

0 · Warm-up from lessons 7 and 13

  1. Lesson 7: the driver's pool is cleared after kill -9 of the primary, and the first write after it took about 10.8 s. What was it waiting for?
  2. Lesson 13: with one of three members frozen, which write concerns still return?

Answers: (1) a new primary. Today we see the 10 s inside that number. (2) w: 1 and w: "majority"; w: 3 times out.

1 · Step by step: the primary is cut off

3-node set, m1 primary (priority 2), m2 and m3 secondaries, all in term 3. I isolate m1 from the network (docker network disconnect) and keep writing to it through docker exec. Timeline from the lab:

  1. 0 s. m1 is isolated. It's still primary and still accepts writes. An insert with w: 1 was acknowledged after 7 ms: that write exists only on m1.
  2. An insert with w: "majority" was applied on m1 too, but it waits for acknowledgements that can't come, and failed with MongoWriteConcernError: waiting for replication timed out at my 2 s wtimeout. Without a wtimeout (and with the implicit default of majority from lesson 6), a plain insertOne waited until m1 stepped down and then failed with not primary. The document existed on m1 in both cases.
  3. ≈10 s. Heartbeats go out every 2 s (heartbeatIntervalMillis). After electionTimeoutMillis = 10 s without a majority of replies, m1 steps down on its own. m2 and m3 have meanwhile seen no primary for 10 s.repl README: step up
  4. 13 s. A secondary runs a dry-run election first (would I win?), then a real one in a new term (4), asking the others for a vote. A member votes yes once per term, and only for a candidate whose oplog is at least as up to date as its own. m2 got m3's vote and 2 of 3 is a majority. It becomes primary, then does a catch-up phase (it won't take writes until it has applied all it knows others have), and writes a "new term" entry to the oplog.candidate perspective
  5. Heal. m1 reconnects, still holding its two inserts at term 3. Its sync source's oplog doesn't contain them: the log says OplogStartMissing: the sync source's oplog and our oplog have diverged, going into rollback. It finds the common point (the last entry both share), uses recoverToStableTimestamp to go back to it, and writes the removed documents to a file before truncating its oplog.

The rollback log line: "Operations reverted by rollback": {"insert": 2, "update": 0, "delete": 0}. The file /data/db/rollback/<collection uuid>/removed.2026-10-30T07-56-11.0.bson held exactly those two documents. bsondump prints them: lost-C (the w:1 insert) and lost-D (the majority attempt that errored). They are not re-applied by MongoDB. Recovering them is a manual job.rollback (RTT)

2 · The commit point: what "safe" means

The majority commit point is an optime such that every entry up to it has been replicated to a majority of members. A primary computes it from the positions the secondaries report (lesson 13, step ④); secondaries learn it from heartbeats and from the metadata on every oplog fetch.commit point propagation

The key rule: a majority-committed write is on at least one member of every possible majority, so any member that can win an election has it. A candidate must have an oplog at least as new as its voters', and any two majorities overlap. So rollback can only ever remove writes that were not majority-committed. In the lab, nothing before the partition was lost (before3, written with w: "majority", was still there).

This is also what read concern means:

Read concernReads…On the isolated old primary (lab)Can see data that is later rolled back?
local (default on primary)The node's latest dataFound the w:1 review (1 doc)Yes
majorityData at or before the commit point0 docsNo

In the lab, isWritablePrimary was still true on the old primary while this read ran, so local returned a review the rest of the set would soon deny existed. (linearizable also contacts a majority; it was not measured here.)

3 · Other ways to run for election

  • Priority takeover. Priority-2 m1 was re-elected after it healed (the term went 4 → 5): a higher-priority member calls an election when it sees a lower-priority primary.
  • Planned stepdown (rs.stepDown()): with election handoff, the old primary asks an up-to-date secondary to run immediately, skipping the 10 s wait. In lesson 7, stepDown gave a new primary in 30–36 ms.
  • Catch-up takeover if a new primary's catch-up takes more than catchUpTakeoverDelayMillis (30 s).

A crash or a partition has no handoff, so you pay the election timeout: ≈ 10 s plus the election (13 s here; 8.3–10.8 s in lessons 7 and 11). During that time there's no primary and writes fail with "not primary" / NotWritablePrimary or wait for server selection (lesson 7). Retryable writes (on by default) retry once.

4 · Lab: partition a primary

About 10 minutes, on the 3-node set from lesson 13. The script lessons/code/0014-failover-lab.sh runs the same steps.

  1. Write a majority document, then cut off the primary: 
    docker network disconnect lab13 lab13-m1
  2. On lab13-m1 (via docker exec), insert with {writeConcern: {w: 1}}. Then run the same insert with {w: "majority", wtimeout: 2000}. Both documents exist locally.
  3. Watch m2 and m3 until one reports isWritablePrimary: true. Write a document there with w: "majority".
  4. Heal with docker network connect lab13 lab13-m1. Check the log for Rollback common point and Operations reverted by rollback, then: 
    docker exec lab13-m1 sh -c 'bsondump /data/db/rollback/*/removed.*.bson'
  5. Predict first: repeat step 2 but with readConcern: "majority" reads on the old primary. How many documents does it find?

6 · So in production you should…

Rule: decide per write whether you can afford to lose it in a failover. If not, use w: "majority" and retryable writes, and treat anything acknowledged with less as "probably saved".

  1. Keep the default w: "majority" (the implicit default since 5.0 on most deployments) for reviews you must keep. Only drop to w: 1 for data you can regenerate, and know the failover window loses it.
  2. Set a wtimeout (or timeoutMS) and handle the error as "unknown outcome", not "failed". In the lab, the timed-out majority insert existed on the old primary and was rolled back later; on a healthy set it may well succeed. Make writes idempotent (a unique key such as the review's _id) so retrying is safe.
  3. Use an odd number of voting members in separate failure domains. With three, losing one still elects; a 2-member set can't elect after losing one. To survive losing a whole site you need voting members in three places (for example 2 + 2 + 1), so that any one site's loss still leaves a majority.
  4. For reads that must not go backwards, use readConcern: "majority", or causally consistent sessions to read your own writes. local is faster but can show data that is rolled back.
  5. Plan for ≈ 10–15 s with no primary on a crash or partition. Make clients tolerate it (retryable writes, serverSelectionTimeoutMS above 15 s) and use rs.stepDown() for maintenance: it's a few tens of milliseconds.
  6. Alert on rollbacks. A rollback/ directory appearing under dbPath (or "Operations reverted by rollback" in the log) means acknowledged writes were lost. Check the removed.*.bson files and re-apply what matters.
