MongoDB Internals · Lesson 0006 · Phase 1: The engine (wrap-up)

One write, end to end

You know the engine's parts now: B-trees, the cache, snapshots, the journal. This lesson follows one insertOne through all of them, and through the layers above them, until the reply comes back.

Your win today: trace one db.reviews.insertOne(…, {w: "majority"}) through nine hops from memory, and, given its slow-query log line, say which hop the time went to. This is the "trace one write end to end" goal from your mission.

0 · Warm-up from lessons 2 to 5

From memory, before reading on. store.reviews has three indexes: _id, {verified: 1, rating: 1} and {tags: 1}. You insert one review with three different tags.

  1. How many WiredTiger tables does the insert touch, and how many keys does it add to the indexes? (lesson 2)
  2. When the insert returns with w: 1, is the review in the .wt file yet? Is it in the journal? (lessons 3 and 5)

Keep your answers. Section 2 counts them, and the lab shows the server's own count.

1 · The nine hops

Here is the whole trip. The architecture map shows the same layers as a stack. This lesson walks them in the order one write crosses them.

  1. 1Driver: build the command as BSON, pick the primary, borrow a connection.
  2. 2Wire: send it as one OP_MSG message.
  3. 3Transport: the connection's SessionWorkflow turns bytes into a request.
  4. 4Command dispatch: find the insert command and run it.
  5. 5One storage transaction: collection record + index keys + oplog entry, committed together.
  6. 6WiredTiger: snapshot, dirty pages in cache, a journal record.
  7. 7Secondaries pull the oplog entry, apply it, and report back.
  8. 8Majority commit point moves past the write; the waiting thread wakes up.
  9. 9Reply: one OP_MSG back to the driver.

Hops 1–6 happen on the primary in well under a millisecond. Hops 7–8 are what w: "majority" adds. Everything below was measured on mongo:8.0 (8.0.34), a 3-node replica set in Docker on one laptop, with 100,000 seeded reviews.

2 · The walkthrough

The review we send (the same one you'll insert in the lab):

db.reviews.insertOne(
  { review: "After two weeks battery lasts for days.", rating: 5,
    tags: ["battery", "quality", "durability"], verified: true },
  { writeConcern: { w: "majority" } })

1Driver: BSON, a primary, a connection

  1. The driver makes the _id. Your document has none, so the driver creates an ObjectId: 4 bytes of time, 5 random bytes, a 3-byte counter.BSON types In my capture it began 6a e0 87 d4, which is the second the insert ran.
  2. It wraps the review in an insert command and adds its own fields: lsid and txnNumber (this makes it a retryable write), $clusterTime, and $db: "store".retryable writes spec
  3. Server selection. The driver keeps a picture of the replica set from its monitoring. Writes can only go to the primary, so it picks m1.server selection spec
  4. Connection pool. It checks out an idle connection to m1 from that server's pool, or opens one if none is free.CMAP spec A full pool means your request waits here, before MongoDB sees anything.

2Wire: the actual bytes

I captured this insert with tcpdump inside the primary's container and decoded it (lab step 6 shows how). It is 483 bytes. Every number is little-endian.wire protocol

Three things to notice:

  • One section, not two. OP_MSG also allows a kind 1 section, a document sequence, so big batches don't have to be nested inside the body.OP_MSG spec mongosh 2.13 put the review inside the body instead. 16 + 4 + 1 + 462 = 483, so there is nothing else.
  • The review is less than a third of the message. 156 of 483 bytes. The rest is the command, the write concern, and driver bookkeeping. That fixed cost per message is one reason insertMany beats a loop of insertOne.
  • The checksum is optional. When a peer sets checksumPresent, mongod checks a CRC-32C, and it computes it with WiredTiger's CRC function.op_msg.cpp

3Transport: Session → ServiceEntryPoint → SessionWorkflow

When mongod accepted this connection, it created a Session object for it. The ServiceEntryPoint gave the session a SessionWorkflow. The workflow reads one message, turns it into a WorkItem, and passes it to ServiceEntryPoint::handleRequest. "A SessionWorkflow can only have one WorkItem in progress at a time."transport README Each connection gets "a new dedicated thread".command dispatch

So one connection runs one command at a time. While our insert waits for the majority (hop 8), that connection is busy. Your driver needs other pooled connections for other requests. That's why w: "majority" under load needs a bigger pool than w: 1.

4Command dispatch: find insert, run it, then wait

The first field of the body, insert, names the command. Commands are registered at startup in a global CommandRegistry. The request is parsed into an invocation of that command.command dispatch For inserts, that's CmdInsert, which calls write_ops_exec::performInserts.write_commands.cpp

Before writing, the server fixes the document: fixDocumentForInsert moves _id to the front.insert.cpp On the wire _id came last. In the stored document and the oplog entry, it's first.

The same code path that runs the command then waits for the write concern, in the same thread (RunCommandAndWaitForWriteConcern).entry point Hold on to that: hop 8 happens here, after the write has already committed.

5One storage transaction, five tables

This is lesson 2 meeting replication. insertDocumentsAtomically opens one WriteUnitOfWork (WUOW) and commits it at the end.write_ops_exec.cpp "All writes in the scope of a WUOW are transactional; they are either all committed or all rolled-back."catalog README Inside it, step by step:collection_write_path.cpp

  1. Collection table. RecordStore::insertRecords adds RecordId → document to the collection's B-tree.
  2. Index tables. indexRecords generates keys for each index and inserts them. A multikey index gets one key per distinct array element, so three tags = three keys. "Collection write operations … perform storage engine writes to both the collection's RecordStore and relevant index's SortedDataInterface in the same storage transaction."catalog README
  3. Oplog entry. Then the OpObserver is called (onInserts), and it writes the oplog entry with logOp.collection_write_path.cppoplog.cpp The oplog is just another collection, local.oplog.rs, so this is the fifth table, still inside the same WUOW. Because this is a retryable write, the primary also records the session's progress in config.transactions.sessions README
  4. Commit. All of it becomes visible at once. There is never a moment when the review exists but its oplog entry doesn't. That's why a secondary can never miss a committed write.

The oplog entry I read back from local.oplog.rs:

{ lsid: { id: UUID('871d…'), uid: … }, txnNumber: Long('2'),
  op: 'i', ns: 'store.reviews',
  ui: UUID('08ef8368-…'),                         // the collection's UUID
  o: { _id: ObjectId('6ae0879de0450d3666115619'),
       review: 'After two weeks battery lasts for days.', rating: 5,
       tags: [ 'battery', 'quality', 'durability' ], verified: true },
  o2: { _id: ObjectId('6ae0879de0450d3666115619') },   // the document key
  stmtId: 0, ts: Timestamp({ t: 1793099677, i: 2 }), t: Long('1'), v: Long('2'),
  wall: ISODate('2026-10-27T11:14:37.664Z'),
  prevOpTime: { ts: Timestamp({ t: 0, i: 0 }), t: Long('-1') } }

op: 'i' is an insert. o is the whole document, _id first. o2 is the document key: _id, plus the shard key on a sharded collection.op_observer_impl.cpp ts + t (term) form the OpTime, the write's position in history.repl README lsid, txnNumber, stmtId and prevOpTime are there because it's a retryable write: they let the server answer a retry without inserting twice.sessions README

6WiredTiger: transaction, cache, journal

You know this part. Briefly, in the order it happens:

  • Transaction (lesson 4). The WUOW is a WiredTiger transaction with its own snapshot. Each insert goes into the in-memory update structures of a leaf page. If another writer changed the same key first, WiredTiger reports a write conflict, and MongoDB retries the whole unit. See lesson 4.
  • Cache (lesson 3). At least one leaf page in each of the five trees is now dirty. The slow log reports the bytes this transaction dirtied as txnBytesDirty. If the cache were past the dirty trigger, this thread would evict before writing. See lesson 3.
  • Journal (lesson 5). On commit, the changes go into a journal record in memory. With w: 1 and no j, the insert does not wait for that record to reach disk; a background sync does it within 100 ms. With j: true, or with w: "majority", the write forces a sync (section 3). The .wt files only get the change later, at eviction or the next checkpoint. See lesson 5.

With w: 1, the trip ends here: jump to hop 9. Answer to warm-up question 2: when w: 1 returns, the review is in the cache and in the in-memory journal buffer, but maybe not on disk anywhere yet.

7–8Secondaries pull; the commit point moves

  1. Pull, not push. "Secondaries drive oplog replication via a pull process." Each secondary's OplogFetcher keeps a tailable find/getMore cursor open on its sync source's oplog, with awaitData, so the getMore waits on the primary until new entries appear.repl README The primary only lets readers see entries with no "holes" behind them, so a secondary can't skip a slower concurrent write.oplog visibility
  2. Apply. The secondary writes the batch to its own oplog and applies it: the same five-table insert as hop 5, on its own copy.
  3. Report. The secondary sends replSetUpdatePosition to its sync source with its lastWritten and lastDurable OpTimes.repl README
  4. Commit point. The majority commit point is the newest OpTime that a majority of members have. The primary moves it forward when it learns of new progress, then "any threads blocking on a writeConcern are woken up". By default it counts lastDurable, so "the server acknowledges a write operation after a majority has written to the on-disk journal."repl README Our thread was waiting in waitForWriteConcern → awaitReplication.write_concern.cpp

9Reply

The reply is another OP_MSG: 230 bytes, with responseTo = 11, the request's requestID. That's how the driver matches the reply to the request. Its body is {n: 1, electionId, opTime: {ts, t}, ok: 1, $clusterTime, operationTime}. The slow-query log for this insert reported reslen: 230, the same number. The opTime in the reply is the oplog entry's ts and t.

3 · What w and j change

The work in hops 1–6 is the same for every write concern. Only the waiting after the commit changes.write concern Measured on the lab replica set: 500 inserts per setting, run twice, p50 latency as seen by mongosh, and journal syncs on the primary per 100 inserts (wiredTiger.log["log sync operations"]).

Write concernReturns afterp50Syncs / 100
{w: 1}Primary committed in memory0.36–0.51 ms0–2
{w: 1, j: true}Primary's journal synced to disk0.80–0.86 ms100
{w: "majority"} (default)Majority have it in their on-disk journal0.94–1.20 ms100
{w: "majority", j: false}Same as above: j: false is ignored0.92–1.10 msn/a
  • w: "majority" is the default. The lab's getDefaultRWConcern showed {w: "majority"} with source implicit.write concern If your code never sets a write concern, it already pays for hops 7–8.
  • "Majority" already means "journaled". With writeConcernMajorityJournalDefault: true (the default), majority writes wait for the journal "even if j: false is set". A write concern that "includes or implies j: true causes an immediate journal synchronization."write concern That's the 100 syncs per 100 writes.
  • These gaps are tiny here because all three nodes share one laptop. In production, w: "majority" adds at least one network round trip to the nearest secondary, plus that secondary's journal sync. Across availability zones, that wait can be bigger than all of hops 1–6 together.

When the majority can't answer

In the lab I paused both secondaries with db.fsyncLock() and inserted a review with {w: "majority", wtimeout: 2000}. After 2 seconds:

MongoWriteConcernError: waiting for replication timed out   (code 64, WriteConcernFailed)
result: { n: 1, opTime: { ts: Timestamp({ t: 1793099705, i: 1 }), t: 1 },
          writeConcernError: { code: 64, errInfo: { wtimeout: true, … } }, ok: 1 }

n: 1 and ok: 1. The review was inserted and stays inserted. The wait timed out, nothing else. A normal read on the primary found it. A read with readConcern: "majority" on the same primary returned nothing, because the primary reads from its own majority-committed snapshot, and the write wasn't in it. After fsyncUnlock(), the majority read returned it. A majority read doesn't ask other nodes anything. "Read concern majority reads do not wait for anything to be committed; they just use different snapshots from local reads."repl README

And if the primary had crashed before any secondary got the write? Another node would become primary without it, and the old primary would roll back the review when it rejoined. That is the risk w: 1 accepts, and what w: "majority" protects you from.rollbacks

6 · So in production you should…

Rule: keep w: "majority" for data you can't lose, always bound the wait with wtimeout or a timeout, and treat a write-concern timeout as "written, not yet safe", never as "failed".

  1. Make retries safe. After a writeConcernError, the review is already on the primary. If you retry blindly, you insert it twice, unless the _id is fixed. Generate the _id in your app (the driver already does) and keep it across retries. Then a retry fails with a duplicate-key error, which you can treat as success. Keep retryable writes on (driver default): they cover one retry after a network error or failover.retryable writes spec
  2. Use w: 1 only where losing a write on failover is acceptable, like view counters or analytics events about reviews. Acknowledged w: 1 writes can be rolled back.
  3. Count your index keys. Every index is another B-tree insert inside the same transaction. A multikey index adds one key per array element: a review with 3 tags costs 3 keys in {tags: 1}. Watch keysInserted in the slow log and drop indexes no query uses.
  4. Batch writes. Each insertOne pays for one message, one dispatch, one transaction commit, one journal sync and one replication wait. insertMany pays those once per batch. In the lab, the request was 483 bytes for a 156-byte review.
  5. Size the pool for the wait. A connection is busy for the whole majority wait (hop 3). If replication slows down, the pool fills up and requests queue in the driver, where the server's metrics can't see them.
